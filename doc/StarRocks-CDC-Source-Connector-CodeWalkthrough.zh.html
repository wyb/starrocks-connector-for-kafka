CDC Source Connector 代码逐文件详解

分支cdc-source-connector-refactor 主代码15 个类 / 约 2500 行 测试131 个

这份文档讲每个文件在做什么、怎么做的。为什么这么设计见《设计文档》，怎么配置和使用见《使用指南》——三者不重复。

1先看全景

15 个类分四层，外加一个跨 sink/source 复用的 common 包。Kafka Connect 只认识其中两个（SourceConnector 和 SourceTask 的实现），其余都是被它们调用的。

一条记录的完整旅程

把文件串起来看，一条变更记录要经过：

Connector.start()      preflight，每张表查表模型/CDC 属性/列，探测 bookmark 函数
Connector.taskConfigs() 表按 round-robin 切给 task
  ↓
Task.start()           每表 fetchColumns + fetchPrimaryKeys，建 ChangeRecordMapper，
                       从 offset store 恢复位点（restoreOffset）
  ↓
Task.poll()            drainPendingReleases → renewLiveBookmarks → bookmarkCreate
                       → 若 head==committed 则跳过 → streamChanges(base, head)
  ↓  StarRocksJdbcClient.streamChanges
     SqlBuilder.changesSql   拼 SQL（含强制 ORDER BY）
     FeConnection.get()      拿连接 + applyStreamingFetchSize
     RowExtractor.extractRow 按 ColumnMeta 取值
  ↓
ChangeRecordMapper.toChangeRecord   Object[] → Debezium envelope SourceRecord
  ↓
Connect 运行时发往 Kafka → commitRecord() 记 ack 水位 → commit() 授权释放
  ↓
下次 Task.poll() 开头 drainPendingReleases() → bookmarkRelease

2入口层

StarRocksCdcSourceConnector207 行

Connect 创建的第一个对象。只做两件事：启动期校验，和把表分配给 task。它不搬运任何数据。

start(props) —— 全部的失败都在这里暴露

建一个临时 CdcClient，对每张表跑 preflightCheckTable，然后用第一张表跑一次 probeBookmarkFunctions，最后 finally 关掉客户端。这个客户端是一次性的，task 后面会各建各的。

preflightCheckTable 的检查顺序：

  1. fetchTableModel → 含 UNQ 或 UNIQUE 直接拒绝（CHANGES 读不了 UNIQUE KEY 表）。两种拼写都匹配，因为 FE 实际发 UNIQUE_KEYS，而文档里写的是 UNQ_KEYS。
  2. 含 PRIMARY 或 PRI → 再查 cdcPropertyEnabled，未开启则拒绝，错误信息里直接给出可复制的 ALTER TABLE 语句。
  3. fetchColumns 遍历每列，三项检查：列名撞上 __CHANGE_TYPE__/__ROW_VERSION__ 则拒绝；isNonExportable 为真（HLL/BITMAP/PERCENTILE）则拒绝；srDataType 为 unknown 则记 WARN 但放行。

整段包在 try/catch (SQLException) 里，任何 SQL 异常都包成 ConnectException 并带上表名——包括"表不存在"。

probeBookmarkFunctions 的 holder 必须独立

它用 config.holderId(name) + ":preflight"，TTL 60 秒。不能复用 task 的 holder：bookmark_create 对同一 holder 是幂等的，表没变化时会返回已存在的那个 bookmark，于是探针的释放会把 task 正在用的位点删掉。常量 PROBE_HOLDER_SUFFIX 存在的唯一理由就是这个。

释放是 best-effort——能证明开关打开的是创建；泄漏的探测 bookmark 60 秒内自己过期。

taskConfigs(maxTasks)

int groups = Math.min(maxTasks, tables.size());
for (int i = 0; i < tables.size(); i++)
    groupTables.get(i % groups).add(tables.get(i));

每组拷一份完整 props，只多塞一个内部键 task.tables。这个键不在 CONFIG_DEF 里，是 Connector 与 Task 之间的私有通道，不对用户暴露。

StarRocksCdcSourceConfig235 行

一个 AbstractConfig：14 个用户可见配置项的 ConfigDef，加上若干读取器。

结构很平——newConfigDef() 是一长串 .define(...)，下面每个配置项一个 getter。值得注意的只有三处：

  • topicFor(table)：先查 table2topic.map，没有映射才回落到 <prefix>.<db>.<table>。
  • holderId(connectorName)：返回 "kc:" + name。这是 bookmark 在服务端的持有者标识，同名 connector 重启后仍认领同一批 bookmark。
  • rejectNoSnapshotWithResnapshot() 在构造函数里跑。
被显式拒绝的组合

snapshot.mode=no_snapshot + nontrackable.policy=resnapshot 会在构造时抛 ConfigException。resnapshot 的自愈方式是丢弃位点、用新快照重建；关掉快照后它什么都读不到，于是会静默丢掉"不可用 base"到"新 bookmark"之间的全部变更，而运维看到的是"表已自愈"。

parseTable2Topic 现在只是 KeyValueListParser.parse 的一行转发。

3状态机层

StarRocksCdcSourceTask448 行 · 正确性核心

poll 循环 + 每表一份 bookmark 状态。整个连接器最容易写错的地方都在这个文件里。

TableState —— 每张表的全部状态

字段含义
cols / pks / mapper启动时解析一次，之后只读
committedBookmark下一个窗口的 base。仅 poll 线程读写
snapshotDone内存标志；不是持久 offset 里那个
lastAckedBookmarkack 水位，由 commitRecord 维护。可能领先已落盘的 offset
releaseFenceBookmark上一轮 commit() 时的 ack 水位。释放围栏
liveBookmarksArrayDeque，已创建未释放，最旧在前。真并发
pendingReleasesConcurrentLinkedQueue，commit 授权、poll 执行
lastRenewMs上次成功续租的时刻。-1 = 尚无成功轮次；全失败的轮次不推进它
lastRenewAttemptMs / renewBackoffMs失败退避：全失败轮次从一个 poll 间隔起步翻倍，租约未知时封顶一分钟、已知后封顶租约/3，成功清零——没有 bookmark_renew 的集群不会被每 poll 热重试
effectiveTtlMs服务端授予的租约。-1 = 尚未得知，0 = 服务端答"永不过期"

前三个字段只在 poll 线程上动，无需同步；中间三个由 synchronized (liveBookmarks) 统一保护——注意两个 long 水位也用这把锁，不是各自独立的；pendingReleases 自带线程安全；最后两个续租字段同样只在 poll 线程上动。

start(props)

读配置 → 建 client → 解析 task.tables → 逐表建 TableState（fetchColumns、fetchPrimaryKeys、建 mapper）→ 从 context.offsetStorageReader() 读回位点交给 restoreOffset。

context 为 null 时（单测直接 new 一个 task）每张表都按首次运行处理，这是刻意留的口子。

restoreOffset(t, raw)

OffsetState state = OffsetState.fromMap(raw);
if (state.snapshotDone) {
    t.committedBookmark = state.bookmarkId;
    t.snapshotDone = true;
    synchronized (t.liveBookmarks) { t.liveBookmarks.addLast(state.bookmarkId); }
}

只信 snapshot_done=true。其余情况（包括完全没有 offset）什么都不做，表保持 fresh，下次 poll 重做全量快照。

最后那行 addLast 不是可选的：恢复出来的 bookmark 必须重新进入存活队列，否则永远没人释放它，每次重启/rebalance 泄漏一个，直到 TTL 到期。

poll() —— 每次调用遍历本 task 的所有表

  1. drainPendingReleases(t)——把上一轮 commit() 授权的释放真正发出去。放在开头是因为所有 JDBC 必须在 poll 线程。
  2. renewLiveBookmarks(t)——到点则给该表持有的每个 bookmark 续租。同样因为 JDBC 只能在这条线程上。
  3. !snapshotDone → 走 bootstrap(t, out) 然后 continue。
  4. head = bookmarkCreate(...)；head == committedBookmark → 本轮无新版本，continue（idle dedup）。
  5. 否则 head 入 liveBookmarks，streamChanges(base, head)，回调里逐行 toChangeRecord；tombstones 开启且是 DELETE 时追加一条墓碑。
  6. 成功后 committedBookmark = head，记一条 INFO。

捕获 NonTrackableException → applyPolicy；捕获 SQLException → 包成 ConnectException 抛出（task 停止）。

全部表都没产出记录时 Thread.sleep(pollIntervalMs) 并返回 null——Connect 的约定是 null 表示"这轮没有数据"。

bootstrap(t, out)

创建 b0 并入队；snapshot.mode=initial 时 streamSnapshot 把全表读出来（每行 toSnapshotRecord(row, b0)），否则只记一条日志。无论哪种，最后都设 committedBookmark = b0; snapshotDone = true;。

renewLiveBookmarks(t) —— 让空闲表不丢位点

没有它，一张长期没有新版本的表会在 source.bookmark.ttlms 之后丢掉 base bookmark：bookmarkCreate 在表未变化时返回同一个 id，但不刷新那个引用的租约，所以连接器每轮看起来都成功，租约却一直在倒计时。bookmark_renew 是唯一能移动这个时钟的入口。

  1. 配置 ttlms <= 0，或服务端已答"永不过期"（effectiveTtlMs == 0）→ 直接返回。
  2. 未到 生效租约 / 3 → 返回。lastRenewMs == -1（尚无成功轮次）不受此门限制。
  3. 处于失败退避窗口内（now - lastRenewAttemptMs < renewBackoffMs）→ 返回。
  4. 锁内只拷贝 liveBookmarks，出锁再发 SQL——commit() 在另一条线程上等这把锁，跨网络持锁会把它一起堵住。
  5. 拷贝为空则不推进计时器：首轮 poll 跑在 bootstrap 之前，那时还没有 bookmark，此时启动时钟会把第一次真正的续租推迟整整一个周期。
  6. 记下尝试时刻（lastRenewAttemptMs = now），逐个 bookmarkRenew，用返回值更新 effectiveTtlMs（-1 记为 0）。
  7. 只有续成了至少一个才推进 lastRenewMs；全失败的轮次设退避后由后续 poll 重试。
三个容易写错的地方

节奏必须用服务端授予的租约，不能用自己配的。真正决定过期的是 min(配置值, bookmark_reference_max_ttl_ms)，后者是 FE 配置、客户端读不到。集群上限设成 1 小时而连接器配 7 天时，按自配值算出的节奏是 56 小时一次——租约照样过期，而此时文档已经宣称问题修好了。

全失败的轮次不能推进节奏时钟。推进了，就等于按配置 TTL 的三分之一再试——集群上限压到 1 小时而配置 7 天时，一次瞬时失败换 56 小时的空窗，引用早被清扫了。退避负责限制重试频率，时钟只认成功。

续租失败不触发 nontrackable.policy。要提前判定"位点已丢"就只能匹配 FE 的异常文案，还会让恢复入口从一处变成两处。续租的职责是阻止过期，不是检测过期；真丢了仍由下一次 CHANGES 读经 classify 走既有策略。

覆盖整个 liveBookmarks 而不只是 committedBookmark：消费端停滞时旧窗口的 bookmark 会长期滞留在保留集里，它们的租约同样在跑。

applyPolicy(t, e)

policy=resnapshot → 记 WARN，把表打回 fresh（snapshotDone=false、committedBookmark=-1），下次 poll 重做快照。不动 liveBookmarks——刚才那次失败的窗口所开的 bookmark 在服务端是真实存在的，仍归 commit() 的规则和 TTL 管。
policy=fail → 记 ERROR 并抛 ConnectException。

commitRecord(record, metadata) —— producer 回调线程

从记录的 sourceOffset 取 bookmark_id，用 tableOf(record) 按 sourcePartition 里的表名找到 TableState，然后 lastAckedBookmark = max(旧值, 本条)。

取 max 而不是"最后一条"，因为同一张表的记录可能乱序 ack。

commit() —— offset committer 线程

long fence = t.releaseFenceBookmark;      // 上一轮的值
t.releaseFenceBookmark = t.lastAckedBookmark;   // 先推进，供下一轮用
if (fence < 0) continue;                  // 首次 commit 什么都不释放
迭代 liveBookmarks，凡 live < fence 的移出并放进 pendingReleases

注意先推进围栏再使用旧值，所以本轮用的永远是一个 commit 周期之前的水位。这个滞后就是全部机制：commitRecord 跑在 producer 发送回调里，而 offset 落盘要等下一次 flush，所以 ack 水位可能领先持久位点；按当前水位释放，会正好删掉那次 flush 刚刚变成持久的那个 bookmark。

这个方法不发任何 SQL，只入队。

OffsetState72 行

Connect offset 的编解码。四个 key 常量 + 两个静态构造 + 一个容错的解析。

sourcePartition = {"db": db, "table": table}
sourceOffset    = {"bookmark_id": <long>, "snapshot_done": <boolean>}

fromMap 的三条容错：raw 为 null 或缺 bookmark_id → fresh()；bookmark_id 可能被反序列化成 Integer 或 Long，统一走 ((Number) v).longValue()；snapshot_done 缺失或不是 Boolean.TRUE → false。

按表拆分 partition 的后果：表之间互相独立，rebalance 把表挪到别的 task 上也能各自恢复。

NonTrackableException54 行

把服务端多种"窗口不可重放"的说法归一化成一个异常类型。

核心是静态的 classify(SQLException)：消息转小写后匹配三种标记之一就包装返回，否则返回 null（调用方原样抛出）。

标记来自
cdc-error-BE 执行期
bookmark + not foundbase 已被释放或过期
not trackableFE 规划期（分区被 drop/重写/reshard）

三种缺一不可：早期只匹配第一种，结果 policy=resnapshot 在生产环境从未生效，而所有单测照常通过。

4数据访问层

CdcClient61 行

10 个方法的接口。存在的意义是让 Task 和 Connector 的单测能注入假实现。

使用者分布并不对称：fetchTableModel/cdcPropertyEnabled 只有 Connector 用，fetchPrimaryKeys/streamSnapshot/streamChanges/bookmarkRenew 只有 Task 用，其余三个两边都用。

bookmarkRenew 是唯一有返回值语义需要留意的：它返回服务端授予的 TTL，而不是传入值——集群侧的上限可能把租约压低，而那个上限客户端读不到。

两个流式方法收 List<ColumnMeta> 而不是列名——它既指定投影哪些列，也决定取值时用哪个 getter，读取端因此永远不会再去问驱动。

StarRocksJdbcClient238 行

接口的唯一实现。拆分后它只剩业务查询，底下三块各管一摊。

方法做什么
bookmarkCreateexecuteOnLeader 拿回字符串结果。null 和非数字都转成 SQLException——直接 parseLong 会抛非受检的 NumberFormatException，逃过 poll 的 catch (SQLException) 直接杀掉 task
bookmarkRenew同样走 executeOnLeader，把返回的生效 TTL 解析成 long；null/非数字同 bookmarkCreate 转 SQLException
bookmarkRelease一行转发
fetchColumns转发给 ColumnMetadataReader
fetchPrimaryKeys读 tables_config.PRIMARY_KEY，逗号切分，逐个 stripBackticksAndWhitespace
fetchTableModel同一行的 TABLE_MODEL；三个方法共用 fetchTableConfigRow
cdcPropertyEnabled同一行的 PROPERTIES——FE 用 Gson().toJson(table.getProperties()) 写出，是 JSON 对象，所以按 key 取而不是在 SHOW CREATE TABLE 文本里做子串匹配（那个格式取决于 FE PrintableMap 的引号与空格，变了就静默失配）。读不出来一律抛，不能答 false——那会让 preflight 叫运维去开一个已经开着的属性
streamSnapshot建 statement → applyStreamingFetchSize → 每行 extractRow 回调
streamChanges同上，另外从 cols.size()+1 和 +2 读出两个伪列；异常先 classify

每个查询方法都以 catch (SQLException e) { connection.closeIfBroken(e); throw e; } 收尾——连接坏了就丢掉，下次 get() 会重建。

FeConnection221 行

连接的一切：URL 扇出、传输判定、复用、leader 轮转、有界重试。

静态初始化块

显式 Class.forName 注册两个驱动。Connect 的每插件类加载器隔离会让 ServiceLoader 发现不到它们，找不到就抛 IllegalStateException 并点名是哪个 artifact。

parseUrls(jdbcUrl)

先 rewriteMariadbScheme（只把 jdbc:mysql:// 换成 jdbc:mariadb://，其余原样），再按 :// 切出 scheme，从 host 列表里找第一个 / 或 ? 作为后缀起点，然后把后缀复制到每一个 host 上。

最后这点是必要的：Arrow Flight 的明文服务端需要 ?useEncryption=false，只挂在最后一个 host 上会让前面的连接全部失败。

executeOnLeader(sql)

两层循环。外层按 URL 个数轮转，内层按 maxRetries() 重试。isLeaderRedirect（消息含 "must run on the FE leader"）→ 关连接、轮转、跳出内层；其他 SQLException → closeIfBroken 后在同一 URL 上重试并 sleep。转满一圈仍未成功则抛出最后一个异常。

STREAM_FETCH_SIZE = 1024，不能是 Integer.MIN_VALUE

MIN_VALUE 是 MySQL Connector/J 的流式习惯用法。MariaDB 驱动对任何负值都抛 SQLException("invalid fetch size")——查询根本发不出去，一行都读不到。Arrow Flight 本来就流式，直接跳过这个调用。

ColumnMetadataReader300 行

权威列清单。两条通道各一套策略，但产出必须一致。

fetchColumns()
 ├─ Arrow  → fetchFromInformationSchema()  ── readInformationSchema() 全用
 └─ MySQL  → fetchFromResultSetMetadata()  ── 驱动描述 + withServerTypes() 补类型名
                                                    └─ readInformationSchema()

MySQL 通道为什么要查两次：ResultSetMetaData 说不出"这列是 ARRAY / JSON / HLL"——它们在 MySQL 协议上都是字符串类型，和 VARCHAR 无法区分。没有服务端的答案，这条通道既不能拒绝无法捕获的表，也不能给 schema 打逻辑类型名，而且同一张表会因为 URL scheme 不同产出不同的 schema。

Arrow 通道为什么不能用驱动描述：实测一张 4 列的表被报成 8 列、全部 nullable=false、precision 和 scale 全为 0。仅可空性一项就是致命的——被描述成 NOT NULL 的列会变成 Connect 的必填字段，第一个 NULL 值就会让 Struct 校验失败。

两条路径都做重名检测。不检的话，问题会在很远的地方浮现成一句光秃秃的 SchemaBuilderException，完全看不出是驱动的元数据有问题。

withServerTypes 按列名做 map 合并，对不上就抛异常——一个没被补上类型名的列，正是 HLL 守卫看不见的那一列。

toJdbcType(dataType) 与 isNonExportable(srDataType)

前者是一个封闭集合的 switch，对应 FE 的 Type.toMysqlDataTypeString()。三组值得注意：

  • bigint unsigned（LARGEINT，128 位）→ OTHER，按文本承载。映射成 BIGINT 会静默截断。
  • array/map/struct/json → OTHER，但显式列出而非落到 default——"已知的复杂类型"和"没见过的类型"在 mapper 里会拿到不同的逻辑名。
  • hll/bitmap/percentile → OTHER，但 isNonExportable 对它们返回 true，preflight 会直接拒绝整张表。

RowExtractor105 行

三个静态方法。看着简单，但类型来源的收敛就发生在这里。

extractValue 的 switch 基于 col.jdbcType，不是 ResultSetMetaData.getColumnType()。后者等于让一条读取路径有两个真相源，而 Arrow 通道上驱动的说法已知不可信。

newUtcCalendar() 每次流式读新建一个：没有显式 Calendar 时驱动会用 JVM 默认时区，本地午夜的 java.sql.Date 会让 converter 在 Connect 的 Date 逻辑类型上抛异常，Timestamp 则静默偏移。Calendar 非线程安全，所以不做共享静态。

末尾统一 return rs.wasNull() ? null : value;——基本类型 getter 对 NULL 返回 0/false，必须靠 wasNull() 纠正。

SqlBuilder104 行 · ColumnMeta58 行

纯函数与值对象，没有状态。

SqlBuilder 里唯一有分量的是 changesSql 末尾那句 ORDER BY __ROW_VERSION__, __CHANGE_TYPE__ DESC：BE 的自然输出是版本降序、同版本内 INSERT 在前，直接透传会让一次 UPDATE 变成"先写新值再删除"，那一行在下游凭空消失。

quoteStr 先转义反斜杠再转义单引号，顺序不能反，否则引号转义引入的反斜杠会被二次转义。

ColumnMeta 同时保留 JDBC 视角（jdbcType/precision/scale/nullable）与 StarRocks 视角（srDataType/srColumnType），因为两者单独都不够用。5 参构造留给测试和无法查服务端的路径。

5记录映射

ChangeRecordMapper286 行

纯函数：Object[] + 列元数据 → Debezium envelope SourceRecord。不碰 JDBC，所以极易测试。

构造函数：所有 schema 只建一次

建四个 schema 加一个 envelope，之后每条记录复用：

  • rowSchema——必须 optional，因为 c 和 d 各有一侧为 null
  • keySchema——无主键时为 null
  • bookmarkSchema / sourceSchema——StarRocks 特有的 {db, table, row_version, bookmark{base, head}}
  • envelope——Envelope.defineSchema().withName(...).withRecord(rowSchema).withSource(sourceSchema).build()

另外建一个 colIndexByName，供 toKeyStruct 按主键列名反查下标。

envelope 必须用 Debezium 的，不能手拼

该库拥有字段集合与顺序（before, after, source, op, ts_ms, transaction）以及各工厂方法打的 op 码。这个顺序是 Avro schema 身份的一部分，下游消费者和 schema registry 会比对；手写的会静默漂移。transaction 恒为 null——CHANGES 流没有事务元数据。

三个产出方法

方法op要点
toChangeRecordc / dchangeType==1 走 envelope.delete（填 before），否则 envelope.create（填 after）。offset 带 snapshot_done=true

变更记录的 row_version 是分区可见版本，从 1 开始递增；bookmark id 来自 FE 全局 id 生成器，大几个数量级。放进去会让每一行快照数据看起来都比其后的所有变更更新，下游若按"仅当 row_version 增大才应用"去重就会把变更全丢掉。

钉住的读跨多个分区、各自处在自己的版本上，本来就没有单一版本可报。要识别"这行来自哪次快照"应看 source.bookmark。

schemaFor(col) —— 类型映射

一个基于 col.jdbcType 的 switch，每个分支按 col.nullable 选 optional 与否。DECIMAL 用 Decimal.builder(col.scale)，DATE/TIMESTAMP 用 Connect 的逻辑类型。

BINARY/VARBINARY/LONGVARBINARY → BYTES。此前它们和取值端同时落到 STRING 默认分支，所以什么都不报错——字节被按连接字符集解码，非法序列变 U+FFFD，不可恢复。因为要两侧同时改，单独回退任何一侧都会立刻抛 DataException。

其余落到 textSchemaFor：srDataType 为 json 用 io.debezium.data.Json，array/map/struct 用 com.starrocks.data.Array/.Map/.Struct，其余为无名的普通 STRING。

putValue 里唯一的特殊处理是 DECIMAL：((BigDecimal) value).setScale(col.scale)，因为 Connect 的 Decimal 逻辑类型要求 scale 与 schema 声明严格一致。

6common 包

Version61 行

版本号的唯一来源。

静态初始化时读 /starrocks-connector.properties——该文件由 Maven 的 <resources><filtering> 在构建期填入 ${project.version}。三种情况返回 "unknown"：资源不存在、值为空、值里还含 ${（说明过滤没跑）。最后一条尤其重要——报字面量 ${project.version} 比承认不知道更糟。

KeyValueListParser67 行

k:v,k:v 格式的唯一解析器，sink 与 source 共用。

四条规则：空值返回空 map；按第一个 : 切分（值里可以有冒号）；任一侧为空则抛；重复 key 直接拒绝而不是后者覆盖。全部失败都抛 ConfigException，绝不返回 null——sink 那份旧实现返回 null，调用方把它当成"映射已禁用"，于是每个 topic 静默路由到同名表。

用 LinkedHashMap 保序，让错误信息和测试都是确定的。

8集成脚本

单测全部注入 FakeCdcClient，所以驱动和服务端的真实行为一律测不到。setFetchSize 那个缺陷让流式读 100% 不可用，而全部单测照常通过——集成冒烟因此是必需的，不是补充。

文件内容
common.sh两套 harness 逐字相同的部分：路径常量、时区固定值、step/fail/note、verify_plugin_jar、stage_plugin_dir
smoke-cluster.sh对接已有集群，12 个步骤。SR_TRANSPORT 切换两条通道
smoke.shDocker 自建环境，共享步骤 0–9

sr_sql、cleanup、start_worker、stop_worker 在两个脚本里同名但实现不同（容器 exec vs 本地进程），所以留在各自脚本里。把同名不同实现的函数合并是合并，不是去重。

12 个步骤在验什么

  1. 0 打包完整性（连接器类、两个驱动、Debezium 三个类、版本资源）+ 集群前置（run_mode、meta functions 开关、OPERATE 权限、FE leader）
  2. 1–2 建表播种、生成 worker 与 connector 配置、建 topic
  3. 3 启动 worker，等到快照记录到达
  4. 4–5 UPDATE/DELETE，然后断言：3 条 op=r、op=d(v=20) 行号早于 op=c(v=200)、DELETE 产出 op=d、envelope 带 transaction 字段
  5. 6 杀 worker 重启，新行以 op=c 出现且快照不重放
  6. 7 DATE/DATETIME 的时区无关取值
  7. 8–9 bookmark 确实被释放，且没有释放失败
  8. 10 VARBINARY 以 base64 AQL/ 到达（op=r 与 op=d 各查一次），JSON/ARRAY/MAP/STRUCT 值完整
  9. 11 preflight 拒绝含 HLL 列的表并指明列名——同时证明 StarRocks 类型名在当前通道上确实传到了守卫

步骤 5 那条顺序断言最关键：它把消费者输出的行序当作消息序，因此 topic 必须是单分区。
