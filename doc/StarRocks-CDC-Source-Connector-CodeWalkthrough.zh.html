1先看全景

13 个类分四层，外加 common 包的 2 个（Version 与 sink 共用，KeyValueListParser 只有 source 用）。Kafka Connect 只认识其中两个（SourceConnector 和 SourceTask 的实现），其余都是被它们调用的。

一条记录的完整旅程

把文件串起来看，一条变更记录要经过：

Connector.start()      preflight，每张表查表模型/CDC 属性/列，探测 bookmark 函数
Connector.taskConfigs() 表按 round-robin 切给 task
  ↓
Task.start()           每表 fetchColumns + fetchKeyColumns，建 ChangeRecordMapper，
                       从 offset store 恢复位点（restoreOffset）
  ↓
Task.poll()            drainPendingReleases → renewLiveBookmarks → bookmarkCreate
                       → 若 head==committed 则跳过 → streamChanges(base, head)
  ↓  StarRocksJdbcClient.streamChanges
     SqlBuilder.changesSql   拼 SQL（含强制 ORDER BY）
     FeConnection.get()      拿连接 + applyStreamingFetchSize
     RowExtractor.extractRow 按 ColumnMeta 取值
  ↓
ChangeRecordMapper.toChangeRecord   Object[] → Debezium envelope SourceRecord
  ↓
Connect 运行时发往 Kafka → offset flush → commit() 读 offset store 后授权释放
  ↓
下次 Task.poll() 开头 drainPendingReleases() → bookmarkRelease

2入口层

StarRocksCdcSourceConnector320 行

Connect 创建的第一个对象。四件事：启动期校验、把表分配给 task、声明精确一次的适用范围、把住 offset 改写的入口。它不搬运任何数据。

start(props) —— 全部的失败都在这里暴露

建一个临时 CdcClient，对每张表跑 preflightCheckTable，然后用第一张表跑一次 probeBookmarkFunctions，最后 finally 关掉客户端。这个客户端是一次性的，task 后面会各建各的。

preflightCheckTable 的检查顺序：

  1. fetchTableModel 为空（null 或空串）→ 直接拒绝。视图、物化视图、外表不是 OlapTable，InformationSchemaDataSource 不会给它们设 table_model，BE 把未设置的 thrift 字段填成 ""——所以"未知"长得像空串而不是 null。把它当放行会让后面每一项检查都通过，表最终死在 bookmark_create。
  2. fetchTableModel → 含 UNQ 或 UNIQUE 直接拒绝（CHANGES 读不了 UNIQUE KEY 表）。两种拼写都匹配，因为 FE 实际发 UNIQUE_KEYS，而文档里写的是 UNQ_KEYS；主键那一侧只需一个子串——"PRIMARY" 本身就含 "PRI"。
  3. 含 PRI → 再查 cdcPropertyEnabled，未开启则拒绝，错误信息里直接给出可复制的 ALTER TABLE 语句。
  4. 含 DUP → 记一条 WARN，见下。AGG 与 PRI 都不警告。
  5. fetchColumns 遍历每列，三项检查：列名撞上 __CHANGE_TYPE__/__ROW_VERSION__ 则拒绝；isNonExportable 为真（HLL/BITMAP/PERCENTILE）则拒绝；isUnrecognized 为真（类型名不在 KNOWN_DATA_TYPES 封闭集里）则记 WARN 但放行——文本能保住值，只是说明 StarRocks 长出了本连接器没听说过的类型。

整段包在 try/catch (SQLException) 里，任何 SQL 异常都包成 ConnectException 并带上表名——包括"表不存在"。

四种模型的 key 列都用得上，但只有 DUP 的不唯一

Kafka key 决定分区，所以同 key 的行进同一分区是保住每个 key 内部顺序的前提。四种模型都有 key 列，FE 也都算了出来，只是 tables_config.PRIMARY_KEY 只对 PRI/UNI 发布；information_schema.columns.COLUMN_KEY 则对每个 key 列填上模型标签（PRI/AGG/DUP/UNI），所以连接器改从那里取。

语义上分三档：PRI 主键唯一；AGG 同 key 的行被聚合成一行，key 同样唯一，因此不警告；DUP 的 key 是排序键、明确允许重复，多行可以共用一个 Kafka key。分区和每 key 顺序不受影响，但日志压缩会删掉本不是重复的行，而且开了 source.tombstones.on.delete 时一条墓碑会连带删掉所有同 key 的行。所以 DUP 记 WARN，不拒绝。

UNIQUE 模型在更早一步就被拒了——CHANGES 读不了它。

probeBookmarkFunctions 的 holder 必须独立

它用 config.holderId(name) + ":preflight"，TTL 60 秒。不能复用 task 的 holder：bookmark_create 对同一 holder 是幂等的，表没变化时会返回已存在的那个 bookmark，于是探针的释放会把 task 正在用的位点删掉。常量 PROBE_HOLDER_SUFFIX 存在的唯一理由就是这个。

释放是 best-effort——能证明开关打开的是创建；泄漏的探测 bookmark 60 秒内自己过期。

taskConfigs(maxTasks)

int groups = Math.min(maxTasks, tables.size());
for (int i = 0; i < tables.size(); i++)
    groupTables.get(i % groups).add(tables.get(i));

每组拷一份完整 props，只多塞一个内部键 task.tables。这个键不在 CONFIG_DEF 里，是 Connector 与 Task 之间的私有通道，不对用户暴露。

exactlyOnceSupport(props) —— 只在不做快照时答 SUPPORTED

source.snapshot.mode=no_snapshot → SUPPORTED；其余（含未设，默认 initial）→ UNSUPPORTED。快照行带 snapshot_done=false，而 restoreOffset 只信 true，所以事务已提交的快照在重启后仍会整份重做——对至少一次这是刻意的，对精确一次正好是它要消灭的重复。CHANGES 窗口没有这个标记：提交的 offset 就是要续的 bookmark，Connect 把它和记录写进同一个事务。

直接读原始 props 而不经 StarRocksCdcSourceConfig：herder 在校验阶段就会调它，半填的配置若在这里抛异常，会变成一条既不点名键也不说原因的校验错误。

alterOffsets(config, offsets) —— 守住 offset REST 接口

SourceConnector 的默认实现返回 false（字节码就是 iconst_0; ireturn）。按 KIP-875 的语义这表示"连接器没有自行处理"，框架照样把运维 PATCH /connectors/{name}/offsets 提交的 JSON 原样写进 offset store——不覆写就等于对任意 payload 敞开。

覆写后逐条校验：offset 为 null 表示重置，先于一切校验放行；否则 partition 必须带非空字符串 db 和 table，bookmark_id 必须是非负 Number，snapshot_done 必须是 Boolean。任一项不满足抛 ConnectException，整个改写请求失败。错误信息里带上值的类型——String 11955 和 Integer 11955 打印出来一模一样。

顺序不能反：DELETE /connectors/{name}/offsets 是把 offset store 里每一个已存 partition 映射成 null 交进来，其中可能有本连接器已经不再写的形状。校验放在 null 判断之前，这类残留就再也清不掉了——重置是唯一的清理入口。

不校验的代价不是立刻报错，而是几分钟后：写进去的畸形 offset 要等到某个 task 重启读回来，才表现为"窗口读不出来"加"续租一直失败"，跟当初那对引号已经联系不起来。

StarRocksCdcSourceConfig296 行

一个 AbstractConfig：14 个用户可见配置项的 ConfigDef，加上若干读取器。

结构很平——newConfigDef() 是一长串 .define(...)，下面每个配置项一个 getter。值得注意的只有三处：

  • topicFor(table)：先查 starrocks.table2topic.map，没有映射才回落到 <prefix>.<db>.<table>。
  • holderId(connectorName)：返回 "kc:" + name。这是 bookmark 在服务端的持有者标识，同名 connector 重启后仍认领同一批 bookmark。
  • 构造函数里跑三道校验：rejectEmptyTableList()——ConfigDef 只查键在不在，一个全是逗号和空白的值会通过却命名了零张表，一处笔误就成了"什么都不发的 source"；rejectDuplicateTableNames()——见下；以及 rejectNoSnapshotWithResnapshot()。三者都在 start() 才跑，Connect 默认的 validate() 不构造这个类，REST 预校验看不到它们。
同一张表不能列两次

重复表名会得到两份 TableState，共用同一个 holder。bookmark_create 对同一 holder 幂等，两份于是拿到同一个 head、开同一个窗口，每行投递两次。被 round-robin 分到两个 task 更糟：A 的 commit() 会释放掉 B 仍在当 base 用的那个 bookmark，B 下一轮 CHANGES 报 not found，凭空触发 source.nontrackable.policy。

只拒完全相同的重复。orders,Orders 放行——服务端是否区分大小写取决于集群，那两个名字可能真是两张表。

被显式拒绝的组合

source.snapshot.mode=no_snapshot + source.nontrackable.policy=resnapshot 会在构造时抛 ConfigException。resnapshot 的自愈方式是丢弃位点、用新快照重建；关掉快照后它什么都读不到，于是会静默丢掉"不可用 base"到"新 bookmark"之间的全部变更，而运维看到的是"表已自愈"。

parseTable2Topic 现在只是 KeyValueListParser.parse 的一行转发。

3状态机层

StarRocksCdcSourceTask622 行 · 正确性核心

poll 循环 + 每表一份 bookmark 状态。整个连接器最容易写错的地方都在这个文件里。

TableState —— 每张表的全部状态

字段含义
cols / pks / mapper启动时解析一次，之后只读
snapshotDone内存标志；不是持久 offset 里那个
committedBookmark（volatile）下一个窗口的 base。poll 线程写、commit 线程读来把释放围栏钳到本 task 自己的位置
liveBookmarksArrayDeque，已创建未释放，最旧在前。真并发
pendingReleasesConcurrentLinkedQueue，commit 授权、poll 执行
lastRenewMs上次成功续租的时刻。-1 = 尚无成功轮次；全失败的轮次不推进它
lastRenewAttemptMs / renewBackoffMs失败退避：全失败轮次从一个 poll 间隔起步翻倍，租约未知时封顶一分钟、已知后封顶租约/3，成功清零——没有 bookmark_renew 的集群不会被每 poll 热重试
effectiveTtlMs服务端授予的租约里最短的那个有限值。-1 = 未知或不设限——初始值如此，全部授予都是 -1（无上限）时也保持如此。永远不会是 0
warnedPollOutpacesLease"poll 间隔喂不饱租约"的 WARN 每表只记一次，不是每轮

只有 liveBookmarks 在监视器下：commit 线程在里面挑出低于围栏的 id，poll 线程在里面追加、并为续租取快照。committedBookmark 用 volatile 而不进监视器，因为读它的那一步（Math.min）不需要与 deque 的修改原子。pendingReleases 自带线程安全，其余字段只在 poll 线程上动。

start(props)

读配置 → 建 client → 解析 task.tables → 逐表建 TableState（fetchColumns、fetchKeyColumns、建 mapper）→ 从 context.offsetStorageReader() 读回位点交给 restoreOffset。

context 为 null 时（单测直接 new 一个 task）每张表都按首次运行处理，这是刻意留的口子。

restoreOffset(t, raw)

OffsetState state = OffsetState.fromMap(raw);
if (state.snapshotDone) {
    t.committedBookmark = state.bookmarkId;
    t.snapshotDone = true;
    retain(t, state.bookmarkId);
}

只信 snapshot_done=true。其余情况（包括完全没有 offset）什么都不做，表保持 fresh，下次 poll 重做全量快照。

最后那行 retain 不是可选的：恢复出来的 bookmark 必须重新进入存活队列，否则永远没人释放它，每次重启/rebalance 泄漏一个，直到 TTL 到期。用 retain 而不是直接 addLast，因为 resnapshot 之后 bootstrap 会拿回同一个 id，重复持有就会被释放两次。

poll() —— 每次调用遍历本 task 的所有表

  1. drainPendingReleases(t)——把上一轮 commit() 授权的释放真正发出去。放在开头是因为所有 JDBC 必须在 poll 线程。
  2. renewLiveBookmarks(t)——到点则给该表持有的每个 bookmark 续租。同样因为 JDBC 只能在这条线程上。
  3. !snapshotDone → 走 bootstrap(t, out) 然后 continue。
  4. head = bookmarkCreate(...)；head == committedBookmark → 本轮无新版本，continue（idle dedup）。
  5. 否则 head 入 liveBookmarks，streamChanges(base, head)。回调不直接写 out，而是把每行连同 changeType 和 rowVersion 缓冲进一个 WindowRow 列表——墓碑要不要发，得看完整个窗口才知道。
  6. 窗口为空（本次 publish 没产生变更行，例如一次 compaction）→ releaseUnusedHead(t, head) 把刚建的 bookmark 交还，位置留在 base，continue。
  7. 否则 appendWindow 展开进 out，只在真删除后面追加墓碑。
  8. demoteAllButLast(out, windowStart, base)：把本窗口除最后一条以外的记录的 offset 改回 base。Connect 提交的是已 ack 的最长前缀而非整批，每条都带 head 时一条 ack 就能让整个窗口显得已持久化。
  9. 成功后 committedBookmark = head，记一条 INFO。
墓碑只跟真删除，不跟 UPDATE 的前半截

BE 的契约是：__CHANGE_TYPE__ 的 1 表示行的 before 值——删除给一条 1，而更新给的是同一个 __ROW_VERSION__ 上的 1（before）加 0（after）。所以"是 DELETE 就发墓碑"会给每一次 UPDATE 也发一条，而墓碑是破坏性信号：compacted topic 据此丢 key，KTable 据此删条目，开了 delete.enabled 的 JDBC sink 据此发 DELETE。后面的 c 会把状态修回来，但中间存在一个所有下游都看得见的假删除。

判据是同一 key 在同一 row version 上有没有对应的 insert：有就是更新的一半，不发。同一次 publish 内删了又插，BE 只暴露两个端点，语义上也是更新，同样不发；跨版本的删除后重插是真删过，照发。

key 为 null 一律不发：墓碑靠 key 认行，没有 key 就删不掉任何东西，只是噪音。

空窗口的 head 必须交还

head 推进了但一行没有时，没有任何记录携带这个 head，于是持久 offset 永远到不了它，commit() 的 fence = min(durable, committedBookmark) 也永远越不过它——每来一次这样的 publish 就泄漏一个 bookmark，renewLiveBookmarks 每轮的续租次数还跟着一起涨。

代价是这类表每轮多一次 leader 语句（创建 + 释放，而不是只创建）。换来的是存活集恒定而不是无界增长。

捕获 NonTrackableException → 先 discardFrom 丢弃本表本轮已产出的记录，再 applyPolicy。捕获 SQLException → 同样 discardFrom（demote 之前每条记录都带 head，一条 ack 就会让读了一半的窗口显得已持久化），记 WARN，然后跳过这张表继续遍历下一张，只留下第一个失败。

不在这里抛，是因为抛异常会让 Connect 丢掉整批返回值，而排在前面的表此刻已经把 committedBookmark 推到了新 head——那批记录既进不了 Kafka，也不会被重读。只有整批为空时才把第一个失败包成 RetriableException 抛出（Connect 只对这一种重试，其余一律杀 task）；否则先把已产出的记录交出去，失败的表下一轮重试。

全部表都没产出记录、也没有失败时 Thread.sleep(pollIntervalMs) 并返回 null——Connect 的约定是 null 表示"这轮没有数据"。

bootstrap(t, out)

创建 b0 并入队；source.snapshot.mode=initial 时 streamSnapshot 把全表读出来（每行 toSnapshotRecord(row, b0)），否则只记一条日志。无论哪种，最后都设 committedBookmark = b0; snapshotDone = true;。

renewLiveBookmarks(t) —— 让空闲表不丢位点

没有它，一张长期没有新版本的表会在 source.bookmark.ttl.ms 之后丢掉 base bookmark：bookmarkCreate 在表未变化时返回同一个 id，但不刷新那个引用的租约，所以连接器每轮看起来都成功，租约却一直在倒计时。bookmark_renew 是唯一能移动这个时钟的入口。

  1. 未到 min(租约 / 3, RENEW_MAX_INTERVAL_MS) → 返回。这里的"租约"是服务端授予的 effectiveTtlMs；尚无授予值时暂用配置的 source.bookmark.ttl.ms，两者都非正则节奏就是上限本身（5 分钟）。lastRenewMs == -1（尚无成功轮次）不受此门限制。没有"服务端答永不过期就不再续租"的分支：source.bookmark.ttl.ms <= 0 只是不设引用级上限，集群上限照样让引用过期，而上限是 mutable 的。
  2. 处于失败退避窗口内（now - lastRenewAttemptMs < renewBackoffMs）→ 返回。三个时刻都取自 monotonicMs()，墙钟回拨不会把间隔撑过它所守护的租约。
  3. 锁内只拷贝 liveBookmarks，出锁再发 SQL——commit() 在另一条线程上等这把锁，跨网络持锁会把它一起堵住。
  4. 拷贝为空则不推进计时器：首轮 poll 跑在 bootstrap 之前，那时还没有 bookmark，此时启动时钟会把第一次真正的续租推迟整整一个周期。
  5. 记下尝试时刻（lastRenewAttemptMs = now），逐个 bookmarkRenew。-1（不设限）算成功但不产生有限值，effectiveTtlMs 因此停在 -1——把它锁定成"永不续租"会在运维随后设上真上限时丢掉全部位点；0 是契约外的答复，记 WARN 后按该个 bookmark 的失败处理。轮内取最短的有限授予值写入 effectiveTtlMs（上限 mutable，同一轮的授予值未必一致）。
  6. 只有续成了至少一个才推进 lastRenewMs；全失败的轮次设退避后由后续 poll 重试。
  7. 成功轮次里若 pollIntervalMs × 3 ≥ 授予租约，每表记一次 WARN：续租只在 poll 开头跑，一个租约里塞不进三次尝试，位点会在没有任何信号的情况下过期，直到下一次 CHANGES 读判定为不可追踪。没有别的地方会报这件事。
三个容易写错的地方

节奏必须用服务端授予的租约，不能用自己配的。真正决定过期的是配置值与 bookmark_reference_max_ttl_ms 中较小的一个，任一侧 <= 0 按不限处理；该上限是 mutable=true 的 FE 配置，随时可变，因此只能以每次返回值为准。集群上限设成 1 小时而连接器配 7 天时，按自配值算出的节奏是 56 小时一次——租约照样过期，而此时文档已经宣称问题修好了。

全失败的轮次不能推进节奏时钟。推进了，就等于按配置 TTL 的三分之一再试——集群上限压到 1 小时而配置 7 天时，一次瞬时失败换 56 小时的空窗，引用早被清扫了。退避负责限制重试频率，时钟只认成功。

续租失败不触发 nontrackable.policy。要提前判定"位点已丢"就只能匹配 FE 的异常文案，还会让恢复入口从一处变成两处。续租的职责是阻止过期，不是检测过期；真丢了仍由下一次 CHANGES 读经 classify 走既有策略。

覆盖整个 liveBookmarks 而不只是 committedBookmark：消费端停滞时旧窗口的 bookmark 会长期滞留在保留集里，它们的租约同样在跑；而且其中任何一个都可能成为 Connect 最终 flush 的位点——某个窗口的记录晚些被 ack，它就是重启恢复点。不能只续首尾：实测在 offset.flush.interval.ms 达到授予租约时，持久位点恰好是被跳过的中间 id。

applyPolicy(t, e)

policy=resnapshot → 记 WARN，把表打回 fresh（snapshotDone=false、committedBookmark=-1），下次 poll 重做快照。不动 liveBookmarks——刚才那次失败的窗口所开的 bookmark 在服务端是真实存在的，仍归 commit() 的规则和 TTL 管。
policy=fail → 记 ERROR 并抛 ConnectException。两条消息末尾都附 leaseStateNote——上次续租距今多久、服务端授予多长——只陈述事实，不推断原因：FE 点名 bookmark 的报错来自分区 drop/重写/reshard，而租约真过期反而表现为 BE 的 ancestor-chain 错误，两个方向都猜错过。

commit() —— offset committer 线程

long durable = durableBookmarkOf(t);      // 读 offset store，读不到为 -1
long fence   = Math.min(durable, t.committedBookmark);
if (fence < 0) continue;
迭代 liveBookmarks，凡 live < fence 的移出并放进 pendingReleases

durableBookmarkOf 走 context.offsetStorageReader().offset(sourcePartition(db, table))，取里面的 bookmark_id。不从"commit() 被调用了"去推断落盘进度：WorkerSourceTask.commitOffsets() 在 shouldFlush 为假时也会调 commitSourceTask()，一次 flush 都没发生。

方向上是安全的：OffsetStorageReaderImpl.offset() 是穿透读，看不到尚未 flush 的写入，所以只会偏旧不会偏新，而偏旧只是这一轮少释放几个。

Math.min 是跨代保护：offset store 以 connector 名而非 task 世代为键，仍在 flush 的僵尸前任会让答案越过本 task 自己的位置，不钳制就会释放掉本 task 刚恢复所依赖的那个 bookmark。

读失败按表隔离——记 WARN、该表推迟到下次 commit()，不影响其余表；读被中断则恢复中断标志并整轮返回，否则剩下每张表都会各自在自己的读上再阻塞一次。

这个方法不发任何 SQL，只读 offset store 和入队。

OffsetState85 行

Connect offset 的编解码。四个 key 常量 + 三个静态构造（fresh、sourcePartition、sourceOffset）+ 一个容错的解析。

sourcePartition = {"db": db, "table": table}
sourceOffset    = {"bookmark_id": <long>, "snapshot_done": <boolean>}

fromMap 只认一种成功：bookmark_id 是非负 Number。raw 为 null、键缺失、值不是 Number（例如被引号包成字符串）、值为负——四种情况都落到 -1 哨兵，一律 fresh()，连 snapshot_done 都不再看。读成 Number 而不是 cast 成 Long，是因为 offset store 走 JSON 往返，小 id 回来是 Integer。

把 -1 和 snapshot_done=true 配在一起会恢复出"快照完成于位点 -1"这种自相矛盾的状态：该表永远跳过快照、从 -1 开窗、续租一个不存在的 bookmark，并且 commit() 的 fence = min(durable, -1) 永远为负，于是再也释放不了任何东西。snapshot_done 不是 Boolean.TRUE 时同样按 false 处理。

按表拆分 partition 的后果：表之间互相独立，rebalance 把表挪到别的 task 上也能各自恢复。

NonTrackableException61 行

把服务端多种"窗口不可重放"的说法归一化成一个异常类型。

核心是静态的 classify(SQLException)：消息转小写后匹配五种写法之一就包装返回，否则返回 null（调用方原样抛出）。

标记来自
cdc-error-BE 执行期
bookmark + not foundbase 已被释放或过期
not trackableFE 规划期（分区被 drop/重写/reshard）
no longer queryablebookmark 解析：分区在快照下被重写或重分布
bookmark + no longer existsbookmark 解析：分区已被 drop

五种缺一不可：早期只匹配第一种，结果 policy=resnapshot 在生产环境从未生效，而所有单测照常通过。

CdcClient87 行

10 个方法的接口。存在的意义是让 Task 和 Connector 的单测能注入假实现。

使用者分布并不对称：fetchTableModel/cdcPropertyEnabled 只有 Connector 用，fetchKeyColumns/streamSnapshot/streamChanges/bookmarkRenew 只有 Task 用，其余四个（bookmarkCreate、bookmarkRelease、fetchColumns、close）两边都用。

bookmarkRenew 是唯一有返回值语义需要留意的：它返回服务端授予的 TTL，而不是传入值——集群侧的上限可能把租约压低，而该上限是 mutable=true 的 FE 配置，随时可变。返回 -1 只说明此刻没有上限，不代表以后没有，所以连接器改为按固定节奏重新探测而不是就此停续。

两个流式方法收 List<ColumnMeta> 而不是列名——它既指定投影哪些列，也决定取值时用哪个 getter，读取端因此永远不会再去问驱动。

StarRocksJdbcClient264 行

接口的唯一实现。拆分后它只剩业务查询，底下三块各管一摊。

FeConnection280 行

连接的一切：URL 扇出、传输判定、复用、leader 轮转、有界重试。

驱动注册——按 URL 只加载一个

构造函数里 Class.forName 注册 driverClassFor(url) 选中的那一个。显式注册是因为 Connect 的每插件类加载器隔离会让 ServiceLoader 发现不到驱动；找不到就抛 IllegalStateException 并点名是哪个 artifact。

两个都注册会在 Java 8 上炸掉 MySQL 通道

Arrow Flight 驱动的 class 文件是 major 55（Java 11），而 pom 的 maven.compiler.target 是 8。Java 8 worker 上 Class.forName 抛的是 UnsupportedClassVersionError——它属于 LinkageError，不是 ClassNotFoundException，所以原来那个点名 artifact 的 IllegalStateException 根本不会执行，异常以 ExceptionInInitializerError 逃出静态块，类被永久毒化，之后每次访问只剩没有 cause 的 NoClassDefFoundError。一个只用 jdbc:mysql:// 的用户，会被一个他根本没用的驱动搞死。

现在按 URL 只加载需要的那个，并且多接一个 catch (LinkageError)，报出 JVM 版本和"为更新的 Java 版本编译"。这条单测钉不住——本机 JVM 上两个驱动都能加载，差异只在 Java 8 上显现；能钉的只有 driverClassFor 的映射。

parseUrls(jdbcUrl)

先 rewriteMariadbScheme（只把 jdbc:mysql:// 换成 jdbc:mariadb://，其余原样），再按 :// 切出 scheme，从 host 列表里找第一个 / 或 ? 作为后缀起点，然后把后缀复制到每一个 host 上。

最后这点是必要的：Arrow Flight 的明文服务端需要 ?useEncryption=false，只挂在最后一个 host 上会让前面的连接全部失败。

executeOnLeader(sql)

两层循环。外层按 URL 个数轮转，内层按 maxRetries() 重试。isLeaderRedirect（消息含 "must run on the FE leader"）→ 关连接、轮转、跳出内层；其他 SQLException → closeIfBroken 后在同一 URL 上重试并 sleep，重试用尽即抛出，不会换到下一个 URL。外层只有 leader 重定向才推进，转满一圈仍未成功则抛出最后一个异常。也就是说逗号分隔的多个 FE 只提供 leader 跟随，不提供节点故障转移——rotateUrl() 全仓只有这一个调用点，数据路径的 get() 始终用当前下标。

STREAM_FETCH_SIZE = 1024，不能是 Integer.MIN_VALUE

MIN_VALUE 是 MySQL Connector/J 的流式习惯用法。MariaDB 驱动对任何负值都抛 SQLException("invalid fetch size")——查询根本发不出去，一行都读不到。Arrow Flight 本来就流式，直接跳过这个调用。

ColumnMetadataReader237 行

权威列清单。两条通道同一条路径：只问服务端。

fetchColumns()
 └─ readInformationSchema()  ──  toJdbcType(DATA_TYPE, COLUMN_TYPE)

为什么完全不用 ResultSetMetaData：Arrow Flight 的驱动实测把一张 4 列的表报成 8 列、全部 nullable=false、precision 与 scale 全为 0；MySQL 协议这边则说不出"这列是 ARRAY / JSON / HLL"——它们和 VARCHAR 完全混同。而且两套描述意味着同一张表会因为 URL scheme 不同产出不同的 schema：StarRocks 的 BOOLEAN 就真的分歧过，一边到达时是 int8，另一边是 boolean。

重名检测在 readInformationSchema 里。不检的话，问题会在很远的地方浮现成一句光秃秃的 SchemaBuilderException。

列表为空即抛 "table not found"——information_schema.columns 对不存在的表返回零行而不是报错。

toJdbcType · isNonExportable · isUnrecognized

前者是一个封闭集合的 switch，对应 FE 的 Type.toMysqlDataTypeString()。四组值得注意：

  • tinyint 要看 COLUMN_TYPE：FE 把 BOOLEAN 的 DATA_TYPE 也写成 tinyint，只有 COLUMN_TYPE 是 tinyint(1)（ScalarType#toMysqlColumnTypeString）。只看类型名，BOOLEAN 会变成 int8。
  • bigint unsigned（LARGEINT，128 位）→ DECIMAL，scale 固定为 0。映射成 BIGINT 会静默截断，按文本承载则把数字变成字符串；Connect 的 Decimal 背后是 BigDecimal，两条传输都能无损承载。FE 对 LARGEINT 不填 NUMERIC_SCALE，所以 scale 由 scaleFor 钉死，不靠 NULL→0 的巧合。
  • array/map/struct/json → OTHER，但显式列出而非落到 default——"已知的复杂类型"和"没见过的类型"在 mapper 里会拿到不同的逻辑名。
  • hll/bitmap/percentile → OTHER，但 isNonExportable 对它们返回 true，preflight 会直接拒绝整张表。

isUnrecognized 是第三个静态方法：类型名不在 KNOWN_DATA_TYPES 里即为真。这个集合逐条镜像 toJdbcType 的 case——switch 自己分不出"有意按文本承载"和"没见过"，两者都是 OTHER。加一个 case 就得加一个名字。

precision/scale 读 NUMERIC_PRECISION/NUMERIC_SCALE，不读 COLUMN_SIZE/DECIMAL_DIGITS：BE 往 COLUMN_SIZE 里填的是 columnLength，一个长度，不是精度。

RowExtractor110 行

三个静态方法。看着简单，但类型来源的收敛就发生在这里。

extractValue 的 switch 基于 col.jdbcType，与 schemaFor 同源，所以 schema 说什么类型就用什么 getter 取。Types.FLOAT 按 JDBC 规范走双精度，Types.REAL 才是单精度。

newUtcCalendar() 每次流式读新建一个：没有显式 Calendar 时驱动会用 JVM 默认时区，本地午夜的 java.sql.Date 会让 converter 在 Connect 的 Date 逻辑类型上抛异常，Timestamp 则静默偏移。Calendar 非线程安全，所以不做共享静态。

末尾统一 return rs.wasNull() ? null : value;——基本类型 getter 对 NULL 返回 0/false，必须靠 wasNull() 纠正。

SqlBuilder130 行 · ColumnMeta61 行

纯函数与值对象，没有状态。

SqlBuilder 里唯一有分量的是 changesSql 末尾那句 ORDER BY __ROW_VERSION__, __CHANGE_TYPE__ DESC：BE 的自然输出是版本降序、同版本内 INSERT 在前，直接透传会让一次 UPDATE 变成"先写新值再删除"，那一行在下游凭空消失。

ChangeRecordMapper315 行

纯函数：Object[] + 列元数据 → Debezium envelope SourceRecord。不碰 JDBC，所以极易测试。

构造函数：所有 schema 只建一次

建四个 schema 加一个 envelope，之后每条记录复用：

  • rowSchema——必须 optional，因为 c 和 d 各有一侧为 null

该库拥有字段集合与顺序（before, after, source, op, ts_ms, transaction）以及各工厂方法打的 op 码。这个顺序是 Avro schema 身份的一部分，下游消费者和 schema registry 会比对；手写的会静默漂移。transaction 恒为 null——CHANGES 流没有事务元数据。

schemaFor(col) —— 类型映射

一个基于 col.jdbcType 的 switch，每个分支按 col.nullable 选 optional 与否。DECIMAL 用 Decimal.builder(col.scale)，DATE/TIMESTAMP 用 Connect 的逻辑类型。

BINARY/VARBINARY/LONGVARBINARY → BYTES。此前它们和取值端同时落到 STRING 默认分支，所以什么都不报错——字节被按连接字符集解码，非法序列变 U+FFFD，不可恢复。因为要两侧同时改，单独回退任何一侧都会立刻抛 DataException。

其余落到 textSchemaFor：srDataType 为 json 用 io.debezium.data.Json，array/map/struct 用 com.starrocks.data.Array/.Map/.Struct，其余为无名的普通 STRING。

bookmarkCreate 的三段逻辑值得留意：队列非空就出队；队列空但见过该表就重复上次的值（这就是 idle dedup 的模拟）；从没编排过就用自增计数器（Connector 的 preflight 探针走这条）。

单测全部注入 FakeCdcClient，所以驱动和服务端的真实行为一律测不到。setFetchSize 那个缺陷让流式读 100% 不可用，而全部单测照常通过——集成冒烟因此是必需的，不是补充。

文件内容
common.sh两套 harness 逐字相同的部分：路径常量、时区固定值、step/fail/note、verify_plugin_jar、stage_plugin_dir
smoke-cluster.sh对接已有集群，12 个步骤。SR_TRANSPORT 切换两条通道
smoke.shDocker 自建环境，9 个步骤（0–8）。断言同源，但编号与 smoke-cluster.sh 并不对齐

sr_sql、cleanup、start_worker、stop_worker 在两个脚本里同名但实现不同（容器 exec vs 本地进程），所以留在各自脚本里。把同名不同实现的函数合并是合并，不是去重。

12 个步骤在验什么

  1. 0 打包完整性（连接器类、MariaDB 驱动、Debezium 三个类、版本资源）+ 集群前置（run_mode 必须是 shared_data、meta functions 开关、OPERATE 权限、FE leader）。Arrow Flight 驱动不在这里查——它在步骤 1 的 SR_TRANSPORT=arrow-flight 分支里，跑 MySQL 协议时根本不检
  2. 1–2 建表播种、生成 worker 与 connector 配置、建 topic
  3. 3 启动 worker，等到快照记录到达
  4. 4–5 UPDATE/DELETE，然后断言：3 条 op=r、同一行（id=2）的 op=d(v=20) 行号早于 op=c(v=200)、DELETE 产出 op=d、BOOLEAN 到达时是 JSON 布尔而 TINYINT 是数字、LARGEINT 以不加引号的完整数字到达（依赖 value.converter.decimal.format=NUMERIC，否则 Decimal 是 base64）、envelope 带 transaction 字段
  5. 6 杀 worker 重启，新行以 op=c 出现且快照不重放
  6. 7 DATE 的时区无关取值；DATETIME 只在 MySQL 协议上断言具体值，arrow-flight 上只要求该列到达（驱动的时间戳取值会按 worker 时区整点偏移，已记为限制）
  7. 8–9 bookmark 确实被释放，且没有释放失败
  8. 10 VARBINARY 以 base64 AQL/ 到达（op=r 与 op=d 各查一次），JSON/ARRAY/MAP/STRUCT 值完整
  9. 11 preflight 拒绝含 HLL 列的表并指明列名——同时证明 StarRocks 类型名在当前通道上确实传到了守卫

步骤 5 那条顺序断言最关键：它把消费者输出的行序当作消息序，因此 topic 必须是单分区。
