1先看全景

18 个类分四层，外加 common 包的 2 个（Version 与 sink 共用，KeyValueListParser 只有 source 用）。数据访问层在复杂类型原生化之后多了 ValueReader 及其两个传输子类（MysqlValueReader/ArrowValueReader）——取值与转换都在这里，按 ColumnType 办事；记录映射层是 ChangeRecordMapper 加类型树（ColumnTypeParser/ColumnType）；DATE/DATETIME 的文本格式住在 ValueReader 基类里，Arrow 专用的换算在它的子类里。

2入口层

StarRocksCdcSourceConnector426 行

Connect 创建的第一个对象。四件事：启动期校验、把表分配给 task、声明精确一次的适用范围、把住 offset 改写的入口。它不搬运任何数据。

start(props) —— 全部的失败都在这里暴露

建一个临时 CdcClient，对每张表跑 preflightCheckTable，然后用第一张表跑一次 probeBookmarkFunctions，最后 finally 关掉客户端。这个客户端是一次性的，task 后面会各建各的。

preflightCheckTable 的检查顺序：

  1. fetchTableConfig 的 model 为 NONE（TABLE_MODEL 为 null 或空串）→ 直接拒绝。视图、物化视图、外表不是 OlapTable，InformationSchemaDataSource 不会给它们设 table_model，BE 把未设置的 thrift 字段填成 ""——所以"未知"长得像空串而不是 null。把它当放行会让后面每一项检查都通过，表最终死在 bookmark_create。
  2. OTHER（不是 FE KeysType 的四个名字，也不是文档里的 UNQ_KEYS）→ 拒绝并点名拼写。StarRocks 长出新模型时在这里暴露，而不是等 CHANGES 读失败。
  3. UNIQUE → 直接拒绝（CHANGES 读不了 UNIQUE KEY 表）。TableConfig.Model.parse 同时认 FE 实际发的 UNIQUE_KEYS 和文档里写的 UNQ_KEYS。
  4. DUPLICATE → 记一条 WARN，见下。AGGREGATE 与 PRIMARY 都不警告。
  5. PRIMARY → 再看 cdcEnabled()（到这一步才解析同一行的 PROPERTIES），未开启则拒绝，错误信息里直接给出可复制的 ALTER TABLE 语句。
  6. fetchColumns 遍历每列，四项检查：列名撞上 __CHANGE_TYPE__/__ROW_VERSION__ 则拒绝；isNonExportable 为真（HLL/BITMAP/PERCENTILE）则拒绝；ARRAY/MAP/STRUCT 列的 COLUMN_TYPE 解析失败（type.kind == OPAQUE）则记 WARN 但放行——该列退化为文本，不会得到错的 schema；isUnrecognized 为真（类型名不在 KNOWN_DATA_TYPES 封闭集里）则记 WARN 但放行——文本能保住值，只是说明 StarRocks 长出了本连接器没听说过的类型。

整段包在 try/catch (SQLException) 里，任何 SQL 异常都包成 ConnectException 并带上表名——包括"表不存在"。

四种模型的 key 列都用得上，但只有 DUP 的不唯一

Kafka key 决定分区，所以同 key 的行进同一分区是保住每个 key 内部顺序的前提。四种模型都有 key 列，FE 也都算了出来，只是 tables_config.PRIMARY_KEY 只对 PRI/UNI 发布；information_schema.columns.COLUMN_KEY 则对每个 key 列填上模型标签（PRI/AGG/DUP/UNI），所以连接器改从那里取，与列的类型信息同一条查询取回，落在 ColumnMeta.key 上。

语义上分三档：PRI 主键唯一；AGG 同 key 的行被聚合成一行，key 同样唯一，因此不警告；DUP 的 key 是排序键、明确允许重复，多行可以共用一个 Kafka key。分区和每 key 顺序不受影响，但日志压缩会删掉本不是重复的行，而且开了 source.tombstones.on.delete 时一条墓碑会连带删掉所有同 key 的行。所以 DUP 记 WARN，不拒绝。

UNIQUE 模型在更早一步就被拒了——CHANGES 读不了它。

probeBookmarkFunctions 的 holder 必须独立

它用 config.holderId() + ":preflight"，TTL 60 秒。不能复用 task 的 holder：bookmark_create 对同一 holder 是幂等的，表没变化时会返回已存在的那个 bookmark，于是探针的释放会把 task 正在用的位点删掉。常量 PROBE_HOLDER_SUFFIX 存在的唯一理由就是这个。

释放是 best-effort——能证明开关打开的是创建；泄漏的探测 bookmark 60 秒内自己过期。

taskConfigs(maxTasks)

int taskCount = Math.min(maxTasks, tables.size());
task k 拿到 tables[k], tables[k + taskCount], tables[k + 2·taskCount], …

每组拷一份完整 props，只多塞一个内部键 task.tables。这个键不在 CONFIG_DEF 里，是 Connector 与 Task 之间的私有通道，不对用户暴露。

exactlyOnceSupport(props) —— 只在不做快照时答 SUPPORTED

source.snapshot.mode=no_snapshot → SUPPORTED；其余（含未设，默认 initial）→ UNSUPPORTED。快照行带 snapshot_done=false，而 restoreOffset 只信 true，所以事务已提交的快照在重启后仍会整份重做——对至少一次这是刻意的，对精确一次正好是它要消灭的重复。CHANGES 窗口没有这个标记：提交的 offset 就是要续的 bookmark，Connect 把它和记录写进同一个事务。

直接读原始 props 而不经 StarRocksCdcSourceConfig：herder 在校验阶段就会调它，半填的配置若在这里抛异常，会变成一条既不点名键也不说原因的校验错误。

alterOffsets(config, offsets) —— 守住 offset REST 接口

SourceConnector 的默认实现返回 false（字节码就是 iconst_0; ireturn）。按 KIP-875 的语义这表示"连接器没有自行处理"，框架照样把运维 PATCH /connectors/{name}/offsets 提交的 JSON 原样写进 offset store——不覆写就等于对任意 payload 敞开。

覆写后逐条校验：offset 为 null 表示重置，先于一切校验放行；否则 partition 必须恰好是非空字符串 db 和 table 两个键（task 按 Map 相等查找，多一个键就再也匹配不上），且库名等于 starrocks.database.name、表名在 starrocks.table.names 里（否则没有任何 task 会读它），bookmark_id 必须是非负 Number，snapshot_done 必须是 Boolean。任一项不满足抛 ConnectException，整个改写请求失败。错误信息里带上值的类型——String 11955 和 Integer 11955 打印出来一模一样。

顺序不能反：DELETE /connectors/{name}/offsets 是把 offset store 里每一个已存 partition 映射成 null 交进来，其中可能有本连接器已经不再写的形状。校验放在 null 判断之前，这类残留就再也清不掉了——重置是唯一的清理入口。

重置多做一步：对请求里每个映射成 null、形如 {db, table} 的 partition，以及请求为空 map 时配置里的每张表（空 map 只可能来自 store 里什么都没存的 DELETE，PATCH 的空请求被 REST 层直接 400），用 createClient 建一个 client，fetchHeldBookmarks 列出 task 的 holder 在这张表上仍持有的引用并逐个 bookmarkRelease（releaseReferences）。DELETE 的清单只有 Connect 已存的 partition，从未落盘的表不在其中，要重置它就 PATCH 它的 partition 为 null；不去动请求没列出的表，因为 PATCH 部分置 null 时越界释放会让别的未落盘表丢变更。原因在 Task 的 restoreOffset：no_snapshot 下没有 offset 时它从最旧的持有引用续读，引用不清，重置在下一次启动就被撤销。这一步需要能解析的配置（parseConfig 把 ConfigException 包成说明用途的 ConnectException）和能应答的 FE，任一释放失败整个重置拒绝，不留半截；本连接器不写的形状（namesATable 为假）没有引用可释放，照旧直接清，不需要配置。表已不存在时 fetchHeldBookmarks 返回空。

不校验的代价不是立刻报错，而是几分钟后：写进去的畸形 offset 要等到某个 task 重启读回来，才表现为"窗口读不出来"加"续租一直失败"，跟当初那对引号已经联系不起来。

文件按 Connect 调用它的顺序排：version/taskClass/config，校验期的 exactlyOnceSupport，start 及其检查（preflightCheckTable 与它的 checkModel/checkColumns 在前，probeBookmarkFunctions 在后，与调用顺序一致），taskConfigs，alterOffsets 与它的助手（parseConfig、releaseReferences、namesATable、requirePartitionString、stringAt、describe），stop；测试注入点 createClient 放最后，与 Task 相同。

StarRocksCdcSourceConfig343 行

一个 AbstractConfig：15 个用户可见配置项的 ConfigDef，加上若干读取器。

结构很平——newConfigDef() 是一长串 .define(...)，下面每个配置项一个 getter。值得注意的只有四处：

  • topicFor(table)：先查 starrocks.table2topic.map，没有映射才回落到 <prefix>.<db>.<table>。
  • holderId()：返回 "kc:" + name，name 取自 Connect 放进 props 的连接器名。这是 bookmark 在服务端的持有者标识，同名 connector 重启后仍认领同一批 bookmark。name 缺失或空白在构造时就拒绝（rejectMissingName）：Connect 给每个 connector 和 task 都放这个键，没有它的配置不是 Connect 生成的，而两个没有名字的连接器会共用一个 holder、位置互串。
  • source.poll.retry.timeout.ms：ConfigDef.Range.atLeast(-1)——-1（永远重试）和 0（首次失败即停）都有含义，再小就是笔误。
  • 构造函数里跑四道校验：rejectMissingName()——见上；rejectEmptyTableList()——ConfigDef 只查键在不在，一个全是逗号和空白的值会通过却命名了零张表，一处笔误就成了"什么都不发的 source"；rejectDuplicateTableNames()——见下；以及 rejectNoSnapshotWithResnapshot()。四者都在 start() 才跑，Connect 默认的 validate() 不构造这个类，REST 预校验看不到它们。
同一张表不能列两次

重复表名会得到两份 TableState，共用同一个 holder。bookmark_create 对同一 holder 幂等，两份于是拿到同一个 head、开同一个窗口，每行投递两次。被 round-robin 分到两个 task 更糟：A 的 commit() 会释放掉 B 仍在当 base 用的那个 bookmark，B 下一轮 CHANGES 报 not found，凭空触发 source.nontrackable.policy。

只拒完全相同的重复。orders,Orders 放行——服务端是否区分大小写取决于集群，那两个名字可能真是两张表。

被显式拒绝的组合

source.snapshot.mode=no_snapshot + source.nontrackable.policy=resnapshot 会在构造时抛 ConfigException。resnapshot 的自愈方式是丢弃位点、用新快照重建；关掉快照后它什么都读不到，于是会静默丢掉"不可用 base"到"新 bookmark"之间的全部变更，而运维看到的是"表已自愈"。

parseTable2Topic 现在只是 KeyValueListParser.parse 的一行转发。

3状态机层

StarRocksCdcSourceTask724 行 · 正确性核心

poll 循环 + 每表一份 bookmark 状态。整个连接器最容易写错的地方都在这个文件里。

文件按生命周期排：start 一组（assignedTables、tableStates、durableOffsets、adoptHeldBookmarks、restoreOffset，按调用顺序），poll 一组（pollTable、bootstrap、窗口整形的 WindowRow/appendWindow/demoteAllButLast/retain/discardFrom，失败处理的 failUnlessRetriable/applyPolicy/leaseStateNote，每轮维护的 drainPendingReleases/renewLiveBookmarks），然后 commit/durableBookmarks/partitionsOf/stop，四个测试桩（createClient、idleSleep、monotonicMs、nanoTime）收尾。下文按同一顺序讲。

TableState —— 每张表的全部状态

字段含义

snapshotDone内存标志；不是持久 offset 里那个

start(props)

读配置 → assignedTables 解析 task.tables，空、重复、不在 starrocks.table.names 里的都拒绝启动（连接器从不生成这三种，出现即手写配置；重复的表会每行发两遍，且一份的围栏会释放另一份的 base）→ 建 client → tableStates 逐表建 TableState（fetchColumns、建 mapper，都是构造参数）→ durableOffsets 把全部表的 partition 一次交给 offsetStorageReader().offsets(...) 读回 raw offset，durableBookmarks 也经它读 → 逐表 adoptHeldBookmarks 把 holder 在这张表上仍持有的引用全部压回 liveBookmarks → restoreOffset。接管在恢复之前：恢复出来的那个 id 通常已在接管名单里，retain 去重。restoreOffset 在每个出口记一行 INFO 说明这张表从哪里开始：持久 offset、最旧的持有引用，或 fresh。

context 为 null 时（单测直接 new 一个 task）每张表都按首次运行处理，这是刻意留的口子。

restoreOffset(t, raw)

OffsetState state = OffsetState.fromMap(raw);
if (state.snapshotDone) {
    t.committedBookmark = state.bookmarkId;
    t.snapshotDone = true;
    retain(t, state.bookmarkId);
    LOG.info("... starts at bookmark {}, the durable offset");
    return;
}
if (snapshotInitial) {
    LOG.info("... starts fresh: the first poll takes the snapshot");
    return;
}
Long oldest = min(t.liveBookmarks);   // adoptHeldBookmarks 已把 holder 仍持有的引用压进来
if (oldest == null) {
    LOG.info("... starts fresh: the first poll pins the current version");
    return;
}
t.committedBookmark = oldest;
t.snapshotDone = true;
LOG.info("... starts at bookmark {}, the oldest reference the holder still holds");

只信 snapshot_done=true。其余情况（包括完全没有 offset）在 initial 模式下什么都不做，表保持 fresh，下次 poll 重做全量快照。no_snapshot 模式没有快照可重做，而第一个变更窗口落盘之前也没有任何 offset：这时 holder 仍持有的最旧 bookmark 就是上一次启动钉住的位置，从它续读，其间的变更一条不少（重复由至少一次兜底，精确一次下被 abort 的事务本来就不可见）。它依赖 adoptHeldBookmarks 先跑：引用列表读不出时记 WARN，表按首次运行处理，这是残留的缺口；引用过了 TTL 同样。运维通过 REST 重置 offset 时，Connector 的 alterOffsets 会先释放这些引用，所以重置仍然意味着"从当前版本开始"。

最后那行 retain 不是可选的：恢复出来的 bookmark 必须重新进入存活队列，否则永远没人释放它，每次重启/rebalance 泄漏一个，直到 TTL 到期。用 retain 而不是直接 addLast，因为 resnapshot 之后 bootstrap 会拿回同一个 id，重复持有就会被释放两次。

adoptHeldBookmarks(t)

启动时先查 information_schema.table_bookmark_references，把 holder 在这张表上仍持有的每个 bookmark 都 retain 进来。restoreOffset 只找回持久 offset 那一个（no_snapshot 下没有 offset 时取其中最旧的续读）；前一个 task 留下的其余引用——窗口没来得及落盘的 head、pendingReleases 里没发出去的释放——原本只能等 TTL（默认 7 天），其中 id 小于持久 offset 的还会成为 FE 的 fence version，vacuum 被卡到过期为止。接管之后它们进入常规规则：低于围栏的在第一次 commit 释放，高于的等窗口越过。查询失败只记 WARN，不影响启动；no_snapshot 下这意味着上一次启动钉住的位置可能找不回来，WARN 里写明了。

poll() —— 每次调用遍历本 task 的所有表

  1. drainPendingReleases(t)——把上一轮 commit() 授权的释放真正发出去。放在开头是因为所有 JDBC 必须在 poll 线程。
  2. renewLiveBookmarks(t)——到点则给该表持有的每个 bookmark 续租。同样因为 JDBC 只能在这条线程上。
  3. !snapshotDone → 走 bootstrap(t, out) 然后 continue。
  4. head = bookmarkCreate(...)；head == committedBookmark → 本轮无新版本，continue（idle dedup）。
  5. 否则 head 入 liveBookmarks，streamChanges(base, head)。回调不直接写 out，而是把每行连同 changeType 和 rowVersion 缓冲进一个 WindowRow 列表——墓碑要不要发，得看完整个窗口才知道。
  6. 窗口为空（本次 publish 没产生变更行，例如一次 compaction）→ 不发记录，但 committedBookmark = head，head 留在 liveBookmarks，continue。
  7. 否则 appendWindow 展开进 out，只在真删除后面追加墓碑。
  8. demoteAllButLast(out, windowStart, base)：把本窗口除最后一条以外的记录的 offset 改回 base。Connect 提交的是已 ack 的最长前缀而非整批，每条都带 head 时一条 ack 就能让整个窗口显得已持久化。
  9. 成功后 committedBookmark = head，记一条 INFO。

第 3 步起的正文在 pollTable(t, out) 里；poll() 本身只剩遍历、异常处理和节流。

墓碑只跟真删除，不跟 UPDATE 的前半截

BE 的契约是：__CHANGE_TYPE__ 的 1 表示行的 before 值——删除给一条 1，而更新给的是同一个 __ROW_VERSION__ 上的 1（before）加 0（after）。所以"是 DELETE 就发墓碑"会给每一次 UPDATE 也发一条，而墓碑是破坏性信号：compacted topic 据此丢 key，KTable 据此删条目，开了 delete.enabled 的 JDBC sink 据此发 DELETE。后面的 c 会把状态修回来，但中间存在一个所有下游都看得见的假删除。

判据是同一 key 在同一 row version 上有没有对应的 insert：有就是更新的一半，不发。同一次 publish 内删了又插，BE 只暴露两个端点，语义上也是更新，同样不发；跨版本的删除后重插是真删过，照发。

key 为 null 一律不发：墓碑靠 key 认行，没有 key 就删不掉任何东西，只是噪音。

空窗口的 head 留下当 base，不交还

FE 的 bookmark_create 只拿最新一个 bookmark 去重，等价条件是各分区 visible version 相同。交还 head 之后，我们持有的 base 对新版本永远不等价，于是每轮都是新建 bookmark、一次空的 CHANGES 扫描、再释放——leader 每轮写两条 edit log，直到下一条真实变更。有过写入之后闲置的表基本都处在这个状态，因为最后一个版本通常是 compaction。

留下 head 并把内存里的 committedBookmark 推到它：下一轮 create 命中 AlreadyAtLatest 返回同一个 id，走 idle 去重；下一个真实窗口以它为 base，记录带上它，持久 offset 就能到达它，fence 也就能释放它。不多钉版本：FE 的 fence version 取 id 最小的存活 bookmark，旧 base 在持久 offset 越过之前一直存活。重启时持久 offset 仍是旧 base，(旧 base, head] 重扫一次，结果还是空。

捕获 NonTrackableException → 先 discardFrom 丢弃本表本轮已产出的记录，再 applyPolicy。捕获 SQLException → 同样 discardFrom（demote 之前每条记录都带 head，一条 ack 就会让读了一半的窗口显得已持久化），记 WARN，然后跳过这张表继续遍历下一张，只留下第一个失败。跳过之前先过一遍 failUnlessRetriable：记下这张表连续失败的起点（firstFailureMs），持续失败达到 source.poll.retry.timeout.ms 就地抛 ConnectException 让 task 失败——批次里其它表的记录随之丢弃，但 task 一死重启就从各自的持久 offset 重读，不丢数据。没有这个上限，列被 drop、权限被收回这类永久错误会让 task 永远 RUNNING 却什么也不交付。

不在这里抛，是因为抛异常会让 Connect 丢掉整批返回值，而排在前面的表此刻已经把 committedBookmark 推到了新 head——那批记录既进不了 Kafka，也不会被重读。只有整批为空时才把第一个失败包成 RetriableException 抛出（Connect 只对这一种重试，其余一律杀 task）；否则先把已产出的记录交出去，失败的表下一轮重试。抛之前先 idleSleep(pollIntervalMs)：Connect 收到 RetriableException 后不等待、立刻再 poll，不自己限速就是一个刷 WARN 的紧循环。

全部表都没产出记录、也没有失败时 idleSleep(pollIntervalMs)（生产即 Thread.sleep）并返回 null——Connect 的约定是 null 表示"这轮没有数据"。

bootstrap(t, out)

创建 b0 并入队；source.snapshot.mode=initial 时 streamSnapshot 把全表读出来（每行 toSnapshotRecord(row, b0)），否则只记一条日志。无论哪种，最后都设 committedBookmark = b0; snapshotDone = true;。

renewLiveBookmarks(t) —— 让空闲表不丢位点

没有它，一张长期没有新版本的表会在 source.bookmark.ttl.ms 之后丢掉 base bookmark：bookmarkCreate 在表未变化时返回同一个 id，但不刷新那个引用的租约，所以连接器每轮看起来都成功，租约却一直在倒计时。bookmark_renew 是唯一能移动这个时钟的入口。

  1. 未到 min(租约 / 3, RENEW_MAX_INTERVAL_MS) → 返回。这里的"租约"是服务端授予的 effectiveTtlMs；尚无授予值时暂用配置的 source.bookmark.ttl.ms，两者都非正则节奏就是上限本身（5 分钟）。lastRenewMs == -1（尚无成功轮次）不受此门限制。没有"服务端答永不过期就不再续租"的分支：source.bookmark.ttl.ms <= 0 只是不设引用级上限，集群上限照样让引用过期，而上限是 mutable 的。
  2. 处于失败退避窗口内（now - lastRenewAttemptMs < renewBackoffMs）→ 返回。三个时刻都取自 monotonicMs()，墙钟回拨不会把间隔撑过它所守护的租约。
  3. 锁内只拷贝 liveBookmarks，出锁再发 SQL——commit() 在另一条线程上等这把锁，跨网络持锁会把它一起堵住。
  4. 拷贝为空则不推进计时器：首轮 poll 跑在 bootstrap 之前，那时还没有 bookmark，此时启动时钟会把第一次真正的续租推迟整整一个周期。
  5. 记下尝试时刻（lastRenewAttemptMs = now），逐个 bookmarkRenew。-1（不设限）算成功但不产生有限值，effectiveTtlMs 因此停在 -1——把它锁定成"永不续租"会在运维随后设上真上限时丢掉全部位点；0 是契约外的答复，记 WARN 后按该个 bookmark 的失败处理。轮内取最短的有限授予值写入 effectiveTtlMs（上限 mutable，同一轮的授予值未必一致）。
  6. 只有续成了至少一个才推进 lastRenewMs；全失败的轮次设退避后由后续 poll 重试。
  7. 成功轮次里若 pollIntervalMs × 3 ≥ 授予租约，每表记一次 WARN：续租只在 poll 开头跑，一个租约里塞不进三次尝试，位点会在没有任何信号的情况下过期，直到下一次 CHANGES 读判定为不可追踪。没有别的地方会报这件事。
三个容易写错的地方

节奏必须用服务端授予的租约，不能用自己配的。真正决定过期的是配置值与 bookmark_reference_max_ttl_ms 中较小的一个，任一侧 <= 0 按不限处理；该上限是 mutable=true 的 FE 配置，随时可变，因此只能以每次返回值为准。集群上限设成 1 小时而连接器配 7 天时，按自配值算出的节奏是 56 小时一次——租约照样过期，而此时文档已经宣称问题修好了。

全失败的轮次不能推进节奏时钟。推进了，就等于按配置 TTL 的三分之一再试——集群上限压到 1 小时而配置 7 天时，一次瞬时失败换 56 小时的空窗，引用早被清扫了。退避负责限制重试频率，时钟只认成功。

续租失败不触发 nontrackable.policy。要提前判定"位点已丢"就只能匹配 FE 的异常文案，还会让恢复入口从一处变成两处。续租的职责是阻止过期，不是检测过期；真丢了仍由下一次 CHANGES 读经 classify 走既有策略。

覆盖整个 liveBookmarks 而不只是 committedBookmark：消费端停滞时旧窗口的 bookmark 会长期滞留在保留集里，它们的租约同样在跑；而且其中任何一个都可能成为 Connect 最终 flush 的位点——某个窗口的记录晚些被 ack，它就是重启恢复点。不能只续首尾：实测在 offset.flush.interval.ms 达到授予租约时，持久位点恰好是被跳过的中间 id。

applyPolicy(t, e)

policy=resnapshot → 记 WARN，把表打回 fresh（snapshotDone=false、committedBookmark=-1），下次 poll 重做快照。不动 liveBookmarks——刚才那次失败的窗口所开的 bookmark 在服务端是真实存在的，仍归 commit() 的规则和 TTL 管。
policy=fail → 记 ERROR 并抛 ConnectException。两条消息末尾都附 leaseStateNote——上次续租距今多久、服务端授予多长——只陈述事实，不推断原因：FE 点名 bookmark 的报错来自分区 drop/重写/reshard，而租约真过期反而表现为 BE 的 ancestor-chain 错误，两个方向都猜错过。

对每张表 t：

  if (fence < 0) continue;

durableBookmarks 经 durableOffsets（start 也用它，partition 列表由 partitionsOf 生成）一次交给 offsetStorageReader().offsets(...)，取每个的 bookmark_id——Connect 的 offset(partition) 只是 offsets(singletonList) 的委托，每次调用都是一趟 offset topic 的读到末尾，逐表读就是 N 趟。不从"commit() 被调用了"去推断落盘进度：WorkerSourceTask.commitOffsets() 在 shouldFlush 为假时也会调 commitSourceTask()，一次 flush 都没发生。

方向上是安全的：OffsetStorageReaderImpl.offsets() 是穿透读，看不到尚未 flush 的写入，所以只会偏旧不会偏新，而偏旧只是这一轮少释放几个。

Math.min 是跨代保护：offset store 以 connector 名而非 task 世代为键，仍在 flush 的僵尸前任会让答案越过本 task 自己的位置，不钳制就会释放掉本 task 刚恢复所依赖的那个 bookmark。

读失败记一条 WARN，全部释放推迟到下次 commit()；读被中断则恢复中断标志后返回——Connect 的 reader 把中断包成 ConnectException，不恢复标志。

这个方法不发任何 SQL，只读 offset store 和入队。

构造函数里 Class.forName 注册 driverClassFor(url) 选中的那一个。显式注册是因为 Connect 的每插件类加载器隔离会让 ServiceLoader 发现不到驱动；找不到就抛 IllegalStateException 并点名是哪个 artifact。

两个都注册会在 Java 8 上炸掉 MySQL 通道

Arrow Flight 驱动的 class 文件是 major 55（Java 11），而 pom 的 maven.compiler.target 是 8。Java 8 worker 上 Class.forName 抛的是 UnsupportedClassVersionError——它属于 LinkageError，不是 ClassNotFoundException，所以原来那个点名 artifact 的 IllegalStateException 根本不会执行，异常以 ExceptionInInitializerError 逃出静态块，类被永久毒化，之后每次访问只剩没有 cause 的 NoClassDefFoundError。一个只用 jdbc:mysql:// 的用户，会被一个他根本没用的驱动搞死。

executeOnLeader(sql)

两层循环。外层按 URL 个数轮转，内层在同一 URL 上最多尝试 source.max.retries 次（是总次数，不是失败后的重试次数）。isLeaderRedirect（消息含 "must run on the FE leader"）→ 关连接、轮转、跳出内层；其他 SQLException → closeIfBroken 后在同一 URL 上重试并 sleep，重试用尽即抛出，不会换到下一个 URL。外层只有 leader 重定向才推进，转满一圈仍未成功则抛出最后一个异常。也就是说逗号分隔的多个 FE 只提供 leader 跟随，不提供节点故障转移——rotateUrl() 全仓只有这一个调用点，数据路径的 get() 始终用当前下标。

STREAM_FETCH_SIZE = 1024，不能是 Integer.MIN_VALUE

MIN_VALUE 是 MySQL Connector/J 的流式习惯用法。MariaDB 驱动对任何负值都抛 SQLException("invalid fetch size")——查询根本发不出去，一行都读不到。Arrow Flight 本来就流式，直接跳过这个调用。

openConnection 在 MySQL 协议的连接上多跑一句 SESSION_SETUP_SQL：SET binary_encoding_format = 'hex', binary_encoding_level = 'nested'。这两个会话变量决定嵌套 VARBINARY 的文本形态，默认值恰好就是这样，但集群可以全局改：raw 会往 MysqlValueReader 扫的文本里塞不可解码的字节，all 会把顶层 VARBINARY 也 hex 化、让 getBytes() 拿到十六进制文本。钉住之后读取器的假设与集群设置无关；SQL 由 MysqlValueReader.SESSION_BINARY_ENCODING 拼出，单测断言两者一致。SET 失败则关掉刚开的连接再抛，不留半初始化的连接。Arrow Flight 以二进制传二进制，不看这两个变量，也就不设。

每次流式读一个实例，把 ResultSet 的一行读成规范化的 Object[]。取值方式和转换规则全部由 ColumnType 决定；两条传输的差别被压进两个子类。

标量走类型化 getter。这是 JDBC 自己的跨驱动转换契约，也是唯一能把 UTC Calendar 交给驱动的地方，所以两个驱动交出同样的东西：BOOLEAN→getBoolean、整数各归各的 getter、FLOAT→getFloat、DOUBLE→getDouble、DECIMAL/LARGEINT→getBigDecimal 后 setScale(声明 scale)（Arrow 把 DECIMALV2 按 scale 9 交回、MariaDB 按声明值，在这里抹平），DATE→getDate(i, utc)→dateText，DATETIME→timestamp()（子类可覆写）→dateTimeText，BYTES→getBytes（getString 会按字符集解码、非法序列变 U+FFFD），STRING/JSON/OPAQUE→getString。wasNull 在 getter 之后统一纠正——基本类型 getter 对 NULL 返回 0/false。

DATE / DATETIME 的文本在基类。dateText/dateTimeText 输出即 StarRocks 自己打印的样子：2026-08-05、2026-08-05 12:34:56，微秒非零才追加六位 .ffffff（BE timestamp::to_string 的规则）。值来自 UTC Calendar 的读取，所以按 UTC 取位得到的就是存储的墙上数字；Timestamp.getTime() 已含小数部分，秒数用 floorDiv 单独取，微秒从 getNanos() 来，普通 java.util.Date 只有毫秒可用。两条传输只此一处格式化；Arrow 专用的天数/微秒入口和时区逆运算在 ArrowValueReader。测试夹具必须按 UTC 构造（LocalDateTime…toInstant(UTC)），Timestamp.valueOf 会按 JVM 默认时区解释数字——第一版夹具就是这么错了 8 小时。

嵌套列没有类型化 getter。getObject 拿到驱动手里的东西，交给子类的 nested()；子类把它整理成"原始树"后回到基类的 readNested()：ARRAY/MAP/STRUCT 的递归、struct 按声明序取字段（缺的为 null，多出的字段名报错——那是 schema 漂移，用 ColumnType.fieldNames 这个解析时建好的集合判定，每个键一次哈希查找）、map 键一律 String.valueOf(leaf(键类型, 原始键))（date 键也因此格式化）、形状不符抛 DataException 并点名类型与实际 class。这些只写一遍。子类只需给出 leaf(kind, raw)：把自己那种原始叶子变成规范标量。

为什么不全走 getObject。两个驱动的 getObject 对标量给的是各自的默认类——MariaDB 把 LARGEINT 当 String、DATETIME 用 Calendar.getInstance() 按 JVM 时区落值，Avatica 按类型码分发——走它会把驱动私有词汇引进转换器，还会让 MySQL 通道本来精确的 UTC 时间路径退化成 DST 跳变时不可逆的找回。取值用契约、转换用类型树，是这条边界的由来。

MysqlValueReader258 行

MySQL 协议唯一的特殊之处：嵌套列到手是 BE put_mysql_row_buffer 拼的文本，像 JSON 但不是 JSON。

内部的 Scanner 先把文本切成类型无关的原始树：[…] 是 List，{k:v,…} 是按键记号索引的 LinkedHashMap，引号里的是字符串记号（单双引号皆可——嵌套 JSON 用单引号包，json_column.cpp:60；只转义 " 与 \，内部允许原始控制字符），裸 null 是 null，其余裸记号原样保留。此时 {1:2} 的裸键（map_column.cpp:591）、'{"a": 1}'、"0102ff" 都只是记号，"它是什么类型"由 leaf(kind, 记号) 按声明类型决定：1/0 是布尔（fixed_length_column_base.cpp:339 走 push_number）、inf/nan 是浮点（fmt 的拼法，Java 不认）、hex 或 base64 解成 byte[]（按 SESSION_BINARY_ENCODING，FeConnection 把会话钉在同一个值上）、date/datetime/json/string 原样。这和 Arrow 侧"Integer 是天数还是 int 由类型说了算"是同一个解法。

出错都是带原文的 DataException：分词错误带偏移量；转换错误（非数字、不认识的布尔值、未声明的 struct 字段）由 nested() 统一补上原文再抛。带引号的 "null" 是字符串，裸的才是 SQL NULL。

ArrowValueReader145 行

Arrow Flight JDBC 驱动的怪癖，且只有怪癖。

顶层两处。驱动的 getTimestamp(i, calendar) 最后一步是 Timestamp.valueOf(LocalDateTime)，按 JVM 默认时区落值、传什么 Calendar 都一样（UTC+8 的 worker 上 12:34:56 变成 04:34:56Z），timestamp() 覆写后经自己的 fromJvmWallClock 逆转（用同一个 JVM 时区 toLocalDateTime() 把 digits 取回，再按 UTC 锚定；DST 跳变那一小时不可逆，是唯一残留）；Avatica 的 getObject 按 JDBC 类型码分发，ARRAY(2003) 拿到 java.sql.Array、MAP/STRUCT(2000) 拿到 vector 的 Map，nested() 先把 Array 用 getArray() 解成 List。这两条都是第一次真集群冒烟才暴露的：字节码里 accessor 的 getObject() 确实返回 List，但 ResultSet.getObject 根本不走那里。

嵌套值是 vector 自己的对象。list 是 List，struct 是字段名到值的 Map，varchar 是 Text（一个非 String 的 CharSequence），DATE 是 Integer 天数、DATETIME 是 Long 微秒——按 class 和 INT/BIGINT 一模一样，所以 leaf() 只看声明类型，再由 dateOfEpochDays/dateTimeOfEpochMicros 换成基类那种文本。嵌套的 map 是 MapVector.getObject 的原样输出，而 MapVector 直接继承 ListVector 的实现——一个由 {key, value} entry map 组成的 List，asMap() 覆写后两种形态都收（review 时抓到的：第一版只认 Map，array<map<…>> 会抛 DataException，单测还喂的是 Map 把错误一起固化了）。

ColumnTypeParser221 行 · ColumnType268 行

把 information_schema.columns.COLUMN_TYPE 解析成带嵌套的类型树，再由类型树生成 Connect schema。复杂列原生化的第一块；ColumnMeta 在构造时调用它，结果驱动 mapper 的 schema 与两条传输的值读取器。

COLUMN_TYPE 是 FE Type.toSql() 的显示串，不是契约，所以解析器只认 FE 会产出的拼法，其余一律 Optional.empty()，调用方回退到按文本承载。嵌套层的拼法：boolean、int(11)、bigint(20)、largeint(40)、decimal(18, 2)（逗号后有空格）、varchar(10)、varbinary(16)、date、datetime、json；唯独 array<> 里的 decimal 走 toString()，拼成 DECIMAL64(18,2)。struct 字段是 `name` type 以 ", " 相连，反引号翻倍转义；字段 COMMENT 未转义直接拼入，深度 ≥15 打成 ...——这两种都以"多出来的 token"形式被拒绝，不需要特判。

ColumnType 和 Connect schema 故意分开：map 的键声明是 int，线上却必须是 STRING（JsonConverter 只在键 schema 为 STRING 时渲染成对象，否则是 [[k,v],…]），而读取器仍要按声明类型去解析传输过来的值。嵌套元素、map 值、struct 字段一律 optional（StarRocks 允许其中任一为 NULL），只有列本身取声明的可空性；嵌套 struct 按路径命名（t.c.a、t.c.c.element），Avro converter 要求 record 名唯一。toConnectValue 是反方向：读取器交出的中立值（标量已转好、数组是 List、map 和 struct 都是 Map<String,Object>）按 schema 装配，struct 递归成 Struct。OPAQUE 是给"按文本承载"的列准备的标量种类，带一个可空的 logicalName；isNested() 判断是不是三种容器之一。

12 个步骤在验什么

  1. 0 打包完整性（连接器类、MariaDB 驱动、Debezium 三个类、版本资源）+ 集群前置（run_mode 必须是 shared_data、meta functions 开关、OPERATE 权限、FE leader）。Arrow Flight 驱动不在这里查——它在步骤 1 的 SR_TRANSPORT=arrow-flight 分支里，跑 MySQL 协议时根本不检
  2. 1–2 建表播种、生成 worker 与 connector 配置、建 topic。表里除标量与 ARRAY/MAP/STRUCT 基本列外，还有六个专挑两条传输分歧点的嵌套元素列：array<date>、array<datetime>（带微秒）、map<int,int>、array<varbinary>、array<boolean>、struct<date, json>
  3. 3 启动 worker，等到快照记录到达
  4. 4–5 UPDATE/DELETE，然后断言：3 条 op=r、同一行（id=2）的 op=d(v=20) 行号早于 op=c(v=200)、DELETE 产出 op=d、BOOLEAN 到达时是 JSON 布尔而 TINYINT 是数字、LARGEINT 以不加引号的完整数字到达（依赖 value.converter.decimal.format=NUMERIC，否则 Decimal 是 base64）、envelope 带 transaction 字段
  5. 6 杀 worker 重启，新行以 op=c 出现且快照不重放
  6. 7 DATE 与 DATETIME 在两条传输上都断言精确字符串。arrow-flight 上驱动的 JVM 时区平移由连接器按传输逆转（第一次真集群冒烟时顶层 ts 是 04:34 而嵌套 adt 是 12:34，同一条记录里自相矛盾，这就是修它的起点）
  7. 8–9 bookmark 确实被释放，且没有释放失败
  8. 10 VARBINARY 以 base64 AQL/ 到达（op=r 与 op=d 各查一次）；ARRAY/MAP/STRUCT 及六个嵌套列按精确 JSON断言（[10,20,30]、{"1":2}、[true,false]、["AQL/"]、{"d":"2026-08-05","j":"{\"a\": 1}"}……），不再是 grep seven；JSON 仍是字符串。随后是传输一致性：把 id=1 快照记录的 after 对象按插件 jar 的校验和留在 $SMOKE_PARITY_DIR（默认 $TMPDIR 或 /tmp 下的 sr-cdc-smoke-parity），另一条传输对同一个 jar 跑完后 diff，不同即失败——这就是"两条传输逐字节相同"的实证
  9. 11 preflight 拒绝含 HLL 列的表并指明列名——同时证明 StarRocks 类型名在当前通道上确实传到了守卫

步骤 5 那条顺序断言最关键：它把消费者输出的行序当作消息序，因此 topic 必须是单分区。
