StarRocks CDC Source Connector 使用指南

版本v1 交付语义at-least-once 状态未提交

1What It Does

StarRocks CDC source connector 是一个 Kafka Connect source（源）连接器——方向与本仓库中已有的 StarRocks sink connector 相反。它会把变更数据捕获（CDC）事件从 StarRocks 的存算分离（云原生）表持续流出到 Kafka topic，每个被捕获的表对应一个 topic。

它在内部通过 FE 的 MySQL 协议（JDBC）驱动 StarRocks 已有的 bookmark 与 CHANGES 基础设施：用 bookmark_create/bookmark_renew/bookmark_release 元函数钉住一个位置（position），通过 [_BOOKMARK_<id>_] 查询提示（query hint）获取某个时间点的初始快照，再通过 [_CHANGES_<base>_<head>_] 查询提示流式获取增量变更。每条记录都以 Debezium envelope（before/after/source/op/ts_ms/transaction，由 Debezium 官方的 io.debezium.data.Envelope 构建）形式发出，其 key 和 value 都是携带 schema 的 Kafka Connect Struct。投递语义为至少一次（at-least-once）。

2前置条件

  • 需要一个 StarRocks 存算分离（云原生）集群。 本连接器依赖的 [_BOOKMARK_]/[_CHANGES_] 查询提示，以及 bookmark 元函数，在存算一体（shared-nothing）集群上不可用。
  • 必须开启 enable_bookmark_meta_functions（默认值为 false）。在每个 FE 上执行： 
    ADMIN SET FRONTEND CONFIG ("enable_bookmark_meta_functions" = "true");
    同时把这一行也加进 fe.conf，以便在 FE 重启后依然生效。
  • 连接用户需要系统级 OPERATE 权限。 bookmark_create/bookmark_renew/bookmark_release 受该权限管控，且只能在当前 FE leader 上执行： 
    GRANT OPERATE ON SYSTEM TO USER 'cdc_user'@'%';
    你不需要自己把连接器指向 leader——在 starrocks.jdbc.url 中列出每一个 FE endpoint，当某次 bookmark 调用报出 "must run on the FE leader" 时，连接器会自动透明地轮转到 leader。
  • PRIMARY KEY 表必须把 enable_change_data_capture 设置为 true——可以在 CREATE TABLE 时设置，也可以提前通过 ALTER TABLE 设置： 
    ALTER TABLE db1.orders SET ("enable_change_data_capture" = "true");
    该属性只适用于存算分离的 PRIMARY KEY 表。请在连接器需要覆盖的版本范围之前就把它打开：该属性关闭期间写入的行无法被重放，任何跨越"关闭"时段的 CHANGES 窗口都会因不可追踪而失败（CDC-ERROR-1 (CHANGE_NOT_TRACKABLE)）。
  • DUPLICATE KEY 和 AGGREGATE KEY 表不需要修改任何表属性即可使用，但仅限于只插入（insert-only）的工作负载。对这类表执行 DELETE/TRUNCATE，或者对任意表进行分区 drop/重写、schema 重写型的 ALTER、bucket 数量或 reshard 变更，都会使跨越该操作的 CHANGES 窗口变为不可追踪——参见限制。
  • 不支持 UNIQUE KEY 表。 CHANGES 无法读取此类表，StarRocksCdcSourceConnector 会在启动时就直接拒绝该配置，而不是留到之后某个 task 运行时才失败。TABLE_MODEL 不是 PRIMARY_KEYS/DUP_KEYS/AGG_KEYS/UNIQUE_KEYS 之一的表同样在启动时被点名拒绝，而不是凭猜测去抓。
  • 除上述条件外，没有额外的 FE 版本要求。 连接器只依赖已经发布的能力（bookmark_create/bookmark_release，以及 [_CHANGES_]/[_BOOKMARK_] 查询提示）；代码中没有最低版本检查。bookmark_renew 是可选增强：集群没有它时续租失败并记日志，空闲表行为退回无续期语义（见限制第 1 条）。

3完整配置示例

starrocks.jdbc.url 指向一个 FE 查询端点——这与 sink 连接器的 starrocks.http.url 不同，后者指向的是 HTTP/stream-load 端口。它的 URL scheme 同时也决定了所使用的传输方式；参见选择传输方式。

键类型默认值说明
starrocks.jdbc.urlString(必填)StarRocks FE 端点的 JDBC URL。多个 FE host 用逗号分隔（例如 jdbc:mysql://fe1:9030,fe2:9030），以便客户端在执行 bookmark 调用时可以轮转到 leader。URL scheme 决定了所使用的传输方式：jdbc:mysql:// 对应 MySQL 协议，jdbc:arrow-flight-sql:// 对应 Arrow Flight SQL——参见选择传输方式。
starrocks.database.nameString(必填)源 StarRocks 数据库的名称。
starrocks.usernameString(必填)用于连接 StarRocks 的用户名。需要 OPERATE 权限。
starrocks.passwordPassword(必填)用于连接 StarRocks 的密码。以 Kafka Connect 的 Password 类型存储，因此会在日志和连接器状态 API 中被掩码处理。
starrocks.table.namesString(必填)需要捕获变更的表名列表，逗号分隔，均属于 starrocks.database.name 指定的数据库。
starrocks.table2topic.mapString""（空）可选的表名到 Kafka topic 名称的映射，格式为 table:topic,table:topic。未在此列出的表会回退使用 source.topic.prefix。
source.topic.prefixStringsr用于为没有在 starrocks.table2topic.map 中显式配置映射的表派生 topic 名称的前缀：topic 名称为 <prefix>.<database>.<table>。
source.snapshot.modeStringinitial是否在开始流式传输变更之前先进行一次初始快照。取值为 initial、no_snapshot 之一。no_snapshot 不能与 source.nontrackable.policy=resnapshot 组合使用——这一组合会在启动时被 ConfigException 直接拒绝，因为 resnapshot 依赖一次全新快照来重建表的位置，而在快照被禁用的情况下它只会静默丢失变更。
source.no.snapshot.missing.position.policyStringfailno_snapshot 下某张表既没有持久 offset、也没有该连接器持有的 bookmark 时的行为：fail 要求显式初始化；latest 在当前版本创建新 bookmark。旧引用过期后也会触发 latest，可能跳过其间的变更。
source.poll.interval.msLong5000在一次未产生任何记录的轮询之后，到下一次轮询之间的休眠毫秒数。
source.snapshot.batch.sizeInt4096每张表每次 poll() 最多返回的快照记录数。快照游标跨批次保持打开，每张正在快照的表使用一条独立的 JDBC 读取连接；此配置不限制 CHANGES 窗口。
source.bookmark.ttl.msLong604800000（7 天）支撑每张表位置的 bookmark 的存活时间（time-to-live），单位为毫秒。task 轮询期间会按服务端实际授予的租约自动续租；TTL 是连接器停止轮询后的兜底——参见限制。取非正值只是不设引用级上限：集群上限 bookmark_reference_max_ttl_ms 照样让 bookmark 过期，因此续租仍会持续；即便服务端回报「永不过期」，也会每五分钟重新探测一次，因为该上限是随时可改的 mutable 配置。
source.nontrackable.policyStringfail当某张表的 CHANGES 窗口变为不可追踪时应采取的动作。取值为 fail、resnapshot 之一。resnapshot 要求 source.snapshot.mode=initial（即默认值）：与 source.snapshot.mode=no_snapshot 组合时会在启动时被 ConfigException 拒绝，因为此时没有任何快照可用于重建该表的位置。
source.tombstones.on.deleteBooleanfalse为 true 时，会在每条删除记录之后立即发出一条额外的 tombstone 记录（value 为 null，key 相同）。
source.max.retriesInt3一次 bookmark 调用在放弃前的尝试次数（对应 sink 连接器的 sink.maxretries）。
source.poll.retry.timeout.msLong600000一张表的读取跨 poll 持续失败多久之后，task 不再重试而是失败。每次失败的 poll 都会先等一个 source.poll.interval.ms 再重试。-1 永远重试；0 首次失败即停。
source.connect.timeout.msInt1000连接 StarRocks 的尝试在超时前等待的毫秒数。sink 连接器的同类配置写作 connect.timeoutms，两者是不同的键。
source.read.timings.enabledBooleanfalse为当前 Connector 统计 JDBC 查询、逐行 next()/解码及 Task 记录映射耗时。将 StarRocksJdbcClient 和 StarRocksCdcSourceTask 的日志设为 DEBUG 后会输出读取和每表 Task 汇总。计时有额外开销，建议仅在排查时开启。

选择传输方式

URL scheme 就是唯一的开关——并不存在单独的传输方式配置项，因为一个 JDBC URL 本身就已经指明了它要使用的驱动（driver）。两种驱动都内置在插件 jar 包中；未被指定使用的那一个则始终保持不活跃（inert）。

MySQL 协议Arrow Flight SQL
URLjdbc:mysql://fe1:9030,fe2:9030jdbc:arrow-flight-sql://fe1:9408?useEncryption=false
端口FE 的 query_port（9030）FE 的 arrow_flight_port
结果路径数据行经由 FE 中转返回FE 负责规划与鉴权；结果批次以列式（columnar）格式直接从 BE流式返回
配置无需要进行集群配置，并为 worker 添加一个 JVM 参数（见下文）

优先使用 MySQL 协议。它不需要任何额外配置，并且对增量窗口而言，数据量通常足够小，FE 一般不会成为瓶颈。当 FE 明显成为瓶颈时，再考虑使用 Arrow Flight——这种情况最常出现在大型初始快照期间，而这部分工作负载本来也只是一次性的。

要使用 Arrow Flight SQL：

  1. 在 fe.conf 和 be.conf 中都设置一个非负的 arrow_flight_port，然后重启。 它默认值为 -1（表示禁用），并且不是一个可变配置（mutable config），因此无法通过 ADMIN SET FRONTEND CONFIG 开启它。
  2. 把 URL 指向该端口，而不是 9030，并保留 ?useEncryption=false，除非你已经配置了 TLS——Arrow 驱动默认会协商使用 TLS，如果不带这个参数，在连接明文（plaintext）服务端时会失败。
  3. 为 Connect worker 打开 java.nio（Java 9+），否则 Arrow 无法分配它的堆外（off-heap）缓冲区： 
    export KAFKA_OPTS="$KAFKA_OPTS --add-opens=java.base/java.nio=ALL-UNNAMED"
    StarRocks 自己的 Arrow Flight 文档把这个参数写成 --add-opens=java.base/java.nio=org.apache.arrow.memory.core,ALL-UNNAMED。当 Arrow 位于 JVM 的 module path 上时，指定模块名是正确的；但在我们这里，驱动被 shade 进 plugin jar、由 Connect 的 plugin classloader 从 classpath 加载，因此并不存在一个名为 org.apache.arrow.memory.core 的具名模块可供 open。实际生效的只有 ALL-UNNAMED 那一半，而模块名那一半只会让每次 JVM 启动都打印一行 WARNING: Unknown module——无害，但没有必要带着。

除此之外，其余部分完全相同：相同的 CHANGES 窗口、相同的 bookmark、相同的 envelope。在这种传输方式下，连接器会跳过仅适用于 MySQL 的流式 fetch-size 调用，因为 Arrow 原生就以 RecordBatch 的形式进行流式传输。

在信任一次 Flight 部署之前，先针对你的集群以 SR_TRANSPORT=arrow-flight 运行集成冒烟测试（integration smoke test）来验证它——该测试会在新的传输方式上运行同一组断言，包括“删除先于插入”的顺序不变式——那是底层驱动发生变化时最容易出现回归的一项。注意它不会在该通道上断言时间类型的取值（脚本只检查列是否存在并打印实际值），原因见限制第 11 条。

每条记录的 key 和 value 都是携带 schema 的 Kafka Connect Struct，因此需要配置支持 schema 的 key.converter/value.converter（例如启用了 schemas.enable=true 的 JsonConverter，或依赖 schema registry 的 Avro/Protobuf converter）。

4消息格式

每条记录都是 Debezium envelope，且由 Debezium 官方的 io.debezium.data.Envelope 构建，而非由本连接器自行拼装，因此其字段顺序就是该库定义的规范顺序：

before, after, source, op, ts_ms, transaction

source 携带 db、table、row_version，以及 bookmark.{base, head}。transaction 恒为 null——StarRocks 的 CHANGES 流不携带事务元数据——但该字段在每条记录的 schema 中都存在，因此消费者和 schema registry 看到的 envelope 形态，与任何其他 Debezium 连接器产生的完全一致。字段顺序是 schema registry 用来比对的 schema 标识的一部分，所以上面这个顺序应当被当作契约，而不是排版格式。

下面的示例都围绕同一个持续演进的场景：一张 PRIMARY KEY 表 db1.orders(id INT, name VARCHAR, qty INT)，以 id 为 key，被捕获到的 topic 是 sr.db1.orders。

为便于阅读，下面的 JSON 按上述规范顺序展示每个 envelope 的逻辑字段取值；实际在网络上传输的字节格式取决于上文配置的 converter（例如 JsonConverter 会是一个 schema+payload 形式的 envelope）。

快照行（op: "r"）

初始快照是钉在同一个 bookmark 上的一次时间点读取，因此它发出的每一行都共享相同的 bookmark.base/bookmark.head——两者都等于该快照所钉住的 bookmark id。快照行的 row_version 永远是 0：一次钉住的读取会跨越多个分区，而每个分区各自处于自己的版本上，因此不存在单一版本可供报告。至于为什么这里不能使用 bookmark id，参见row_version 在不同记录类型中的表现。

{
  "before": null,
  "after": { "id": 1, "name": "widget", "qty": 10 },
  "source": {
    "db": "db1",
    "table": "orders",
    "row_version": 0,
    "bookmark": { "base": 1000, "head": 1000 }
  },
  "op": "r",
  "ts_ms": 1700000000000,
  "transaction": null
}

Key：{ "id": 1 }。（紧接着会有第二条 op: "r" 记录，对应 id: 2，source 取值相同。）

row_version 在不同记录类型中的表现

source.row_version 和 source.bookmark.{base,head} 是两个完全不同的编号空间，这个区别在编写消费者逻辑时至关重要：

字段编号空间典型量级
op: "c" / op: "d" 上的 row_version该分区的可见版本（visible version）——从 1 开始，每次 publish 加 1较小，例如 3、4、5
op: "r" 上的 row_version无意义；恒为 00
bookmark.base / bookmark.headFE 全局 ID 生成器，与表 ID、tablet ID 共用同一套编号较大，例如 11952

不要把 bookmark id 与 row_version 相比较，也不要把 row_version 当作跨记录的排序依据。在同一个 Kafka partition 内，broker 自身的 offset 顺序已经给出了正确的先后关系——快照行在前，随后是按提交顺序排列的变更——因此按 offset 排序既足够又更安全。row_version 最好被当作诊断性的元数据来看待：它告诉你某个变更来自 StarRocks 的哪一次 publish，也正是它让一次 UPDATE 的两半（删除和插入）可以被识别为同一个事件（因为它们共享同一个值）。

插入（op: "c"）

一次 INSERT 写入 (3, 'thingamajig', 30)，会被下一次轮询捕获到（base 是上一次已提交的 bookmark，head 是本次轮询刚创建的 bookmark）：

{
  "before": null,
  "after": { "id": 3, "name": "thingamajig", "qty": 30 },
  "source": {
    "db": "db1",
    "table": "orders",
    "row_version": 4,
    "bookmark": { "base": 1000, "head": 1010 }
  },
  "op": "c",
  "ts_ms": 1700000005000,
  "transaction": null
}

Key：{ "id": 3 }。

更新（op: "d" + op: "c"，相同 key）

这里没有专门的 op: "u"。StarRocks 的 CHANGES 窗口把一次 SQL UPDATE 表示为一对操作——删除旧值、插入新值，且两者的 row_version 相同；连接器原样保留这种配对：对同一个 key，总是先发出删除记录，再发出插入记录。一条 UPDATE ... SET qty = 300 WHERE id = 3 会产生：

{
  "before": { "id": 3, "name": "thingamajig", "qty": 30 },
  "after": null,
  "source": {
    "db": "db1",
    "table": "orders",
    "row_version": 5,
    "bookmark": { "base": 1010, "head": 1020 }
  },
  "op": "d",
  "ts_ms": 1700000010000,
  "transaction": null
}
{
  "before": null,
  "after": { "id": 3, "name": "thingamajig", "qty": 300 },
  "source": {
    "db": "db1",
    "table": "orders",
    "row_version": 5,
    "bookmark": { "base": 1010, "head": 1020 }
  },
  "op": "c",
  "ts_ms": 1700000010001,
  "transaction": null
}

两条记录共享 key { "id": 3 } 和 source.row_version: 5，并且在同一个窗口内，对同一个 key，删除记录总是产生在插入记录之前。

删除（op: "d"）

一次 DELETE FROM db1.orders WHERE id = 2：

{
  "before": { "id": 2, "name": "gadget", "qty": 20 },
  "after": null,
  "source": {
    "db": "db1",
    "table": "orders",
    "row_version": 6,
    "bookmark": { "base": 1020, "head": 1030 }
  },
  "op": "d",
  "ts_ms": 1700000015000,
  "transaction": null
}

Key：{ "id": 2 }。如果 source.tombstones.on.delete=true，这条记录之后会立即跟着一条独立的 tombstone（墓碑）记录：它与删除记录共享相同的 key（及 key schema）、目标 topic，以及 Kafka Connect 内部的 sourcePartition/sourceOffset 记录（这是连接器自身用于恢复的 checkpoint，并非 Kafka broker 分配的 partition/offset），但它本身是一条独立的 Kafka 消息，value 为 null、value schema 也为 null——这是 Kafka Connect 中用于触发下游日志压缩（log compaction）的常规信号。

Key 与无 key 的表

Kafka 记录的 key 是一个由该表 key 列构成的 Struct——PRIMARY KEY 表的主键、AGGREGATE KEY 表的聚合键、DUPLICATE KEY 表的排序键，information_schema.columns.COLUMN_KEY 对每种模型都会标出它们——同一张表的所有记录使用相同的 key schema。DUPLICATE KEY 的排序键不唯一，多行可以共享同一个 Kafka key，这对压缩和墓碑意味着什么参见限制。完全没有 key 列的表，记录的 key 为 null。

ARRAY / MAP / STRUCT原生的 array / map / struct schema，JSON 里是数组 / 对象 / 对象；元素类型按同表映射，嵌套元素均可空。MAP 的键一律为 STRING（JsonConverter 只在键为 STRING 时输出对象），struct 字段按声明顺序。嵌套类型取自 information_schema.columns.COLUMN_TYPE；解析不了的列（例如 struct 字段带 COMMENT）退化为 STRING 并带逻辑名 com.starrocks.data.Array / .Map / .Struct，启动时 WARN 一次
HLL / BITMAP / PERCENTILE启动时直接拒绝

复杂类型目前按文本承载，不是 Connect 的 ARRAY/MAP/STRUCT。值本身完整保留（就是 StarRocks 渲染出的文本），下游拿不到的是可供投影的嵌套 schema。schema 上的逻辑名是为了让消费者无需了解源表，就能把「结构化文本」和「普通字符串」区分开。

ARRAY/MAP/STRUCT 刻意不使用 io.debezium.data.Json：它们渲染出的形态确实像 JSON，但用那个名字等于承诺每个值都能按 JSON 解析，而这一点在边界情况上（NULL、内嵌引号、深层嵌套）尚未验证。逻辑名只说明这一列是什么，不对文本如何解析作任何承诺。

HLL/BITMAP/PERCENTILE 存的是聚合中间态而非值：直接 SELECT 出来的内容消费者既无法解释也无法回灌。含这类列的表会在 preflight 阶段被拒绝并指明是哪一列，而不是启动后源源不断地往 Kafka 发无意义内容。视图同样抓不了（它没有表模型），所以只能把这张表从 starrocks.table.names 里去掉，或者删掉该列。

5语义

启动、轮询与异常处理

task 按表恢复位置。启动时先读取 Connect offset，再查询连接器 holder（kc: 加连接器名称）在 FE 上仍持有的 bookmark；下表按优先级从上往下判断。无效或缺失的 bookmark_id 不构成可恢复位置，只有 snapshot_done=true 的有效 offset 才会直接用于增量续读。

启动时的状态处理方式
有有效 Connect offset，且 snapshot_done=true从 offset 中的 bookmark 续读；它优先于 holder 的其它引用。
没有上述 offset，source.snapshot.mode=initial从头读取该表快照；即使快照此前已有部分记录落盘，重启后也会重做。
没有上述 offset，no_snapshot，holder 仍有引用从最旧的持有 bookmark 续读。
no_snapshot，offset 和 holder 引用都没有，缺位点策略为 fail（默认）启动失败；无法区分首次启动和旧引用已过期。
no_snapshot，offset 和 holder 引用都没有，缺位点策略为 latest首次 poll() 在当前版本创建 bookmark，只读取此后的变更；不会输出已有行，可能跳过旧引用过期以来的变更。

不能把查询失败当成“没有引用”。no_snapshot 没有可用 offset 时，如果 FE 的引用列表查询失败，即使配置了 latest 也会启动失败。有可用 offset 或使用 initial 时，查询失败只记录警告，遗留引用暂时无法接管或释放。配置、表列元数据或 Connect offset 读取失败同样使启动失败。

启动成功后，每轮 poll() 依次处理分配给 task 的表。initial 快照按每表每轮最多 source.snapshot.batch.size 行返回；快照完成后，或 no_snapshot 已有起点时，创建 head bookmark 并读取完整的 CHANGES(base, head) 窗口。head 等于 base 时不发记录；窗口没有变更行时仅在内存中推进 base。有记录时保持更新的 delete→insert 顺序；只有窗口最后一条记录携带 head offset，其余携带 base offset；开启 tombstone 后也只在真实删除后追加墓碑。

运行中的情况当前处理方式
普通 SQL 读取失败，含读取到一半失败丢弃该表本轮的部分结果并关闭快照游标，下轮重试；其它表已产生的记录仍可返回。整轮没有记录时，等待 source.poll.interval.ms 后抛 RetriableException。连续失败达到 source.poll.retry.timeout.ms（默认 10 分钟）则 task 失败；-1 一直重试，0 首次即失败。
CHANGES 窗口不可追踪丢弃该表本轮结果。默认 source.nontrackable.policy=fail 立即使 task 失败；resnapshot 在下轮重新读取整表快照，仅允许与 initial 组合。source.no.snapshot.missing.position.policy=latest 不处理已有位点的不可追踪错误。
bookmark 续租失败记录警告并退避重试，不立即宣布位置丢失。task 停止、暂停或长时间不能再次 poll() 时无法续租；位置真正失效会在后续 CHANGES 读取中暴露。
bookmark 释放失败保留待释放项，下轮 poll() 重试。只有低于 Connect 已持久化 offset 与本 task 内存位置两者围栏的旧 bookmark 才会被释放。
task 停止或读取中被停止唤醒空闲轮询、关闭游标和 client；读取线程以中断方式退出，不把停止当成普通 SQL 错误重试。

latest 首次创建 bookmark 不产生记录，因此 Connect 可能尚未持久化 offset。此时重启会先尝试 holder 仍持有的 bookmark；若它也过期，latest 会再次建立新起点。只有 no_snapshot 且缺位点策略为 fail 时，连接器才报告支持 exactly-once。

no_snapshot 缺少位点时

设置 source.no.snapshot.missing.position.policy=latest 后，某张表既没有持久 Connect offset、也没有该连接器仍持有的 bookmark 时，会自动从当前 StarRocks 版本开始，只读取此后的变更，不会输出表中已有的行。停机时间长到旧引用过期时也会如此，旧位点到新位点之间的变更会被跳过。如果 holder 仍有 bookmark，即使 offset 缺失也优先从最旧的引用续读。此配置不覆盖已有持久 offset，也不处理不可追踪的 CHANGES 窗口。默认值 fail 会让 task 停止，等待明确选择。

选择 fail 并需要手工建立起点时，执行以下步骤。

在支持 offset 管理 API 的 Connect worker（Kafka 3.6+）上创建连接器后，先用 PUT /connectors/starrocks-cdc-orders/stop 停止它，再初始化 offset。停止前 task 可能因没有位点而失败，这是预期行为，不会输出记录。对每张捕获表，在 StarRocks FE leader 上执行 SELECT bookmark_create('db1', 'orders', 'kc:starrocks-cdc-orders', '604800000')，然后在连接器处于 STOPPED 状态时，把返回的数值 bookmark id 写入 PATCH /connectors/starrocks-cdc-orders/offsets：

{"offsets":[{"partition":{"db":"db1","table":"orders"},"offset":{"bookmark_id":11955,"snapshot_done":true}}]}

holder 是 kc: 加连接器的 name；TTL 参数取 source.bookmark.ttl.ms。为每张表初始化，使用 GET /connectors/starrocks-cdc-orders/offsets 确认写入，再于授予租约过期前调用 PUT /connectors/starrocks-cdc-orders/resume。捕获起点是创建 bookmark 时的版本；此前的变更不在本次捕获范围内。没有持久 offset 时，task 可以从 holder 仍持有的最旧 bookmark 续读。选择 fail 后，显式重置 offset 也需要重新初始化。参见 Kafka Connect REST API。

  • 精确一次（exactly-once）仅支持 no_snapshot 且缺位点策略为 fail。 在 distributed 模式的 worker 上开启 exactly.once.source.support=enabled（需 Kafka 3.3+），Connect 会把每次 poll 的记录与其 offset 放进同一个 producer 事务，崩溃在提交之前则整批 abort，read_committed 的消费者看不到。source.snapshot.mode=initial 时连接器报告 UNSUPPORTED：快照行带 snapshot_done=false，重启时整份重做，已提交的行会重复。缺位点策略为 latest 时也报告 UNSUPPORTED，因为它可能跳过旧位点到当前版本之间的变更。
  • 重置 offset 会连带释放 FE 上的引用。 连接器处于 STOPPED 时执行 DELETE /connectors/{name}/offsets，alterOffsets 会释放 task 的 holder 在每张 Connect 存有 offset 的表上仍持有的每一个 bookmark——store 里一张都没存时则是配置里的每张表。从未落盘的表（no_snapshot 下第一个变更窗口之前）不在带有其它表的 DELETE 清单里，要重置它，用 PATCH 把它的 partition 置为 null。用旧名字重建的连接器会继承该名字的引用，一次 DELETE 即可清掉。这些都需要能解析的配置和能应答的 FE；任一释放失败则整个重置被拒绝，什么也不写。no_snapshot 重置后按缺位点策略处理：fail 要求重新初始化，latest 从当前版本开始。带显式 offset 的 PATCH 仅校验形状：bookmark_id 必须是非负数、snapshot_done 必须是布尔值，且表在配置里。
  • 至少一次（at-least-once）投递（默认）。 一张表旧的 bookmark 只会在 task 的 commit() 回调中被释放，而且只释放低于 task 从 Connect 自己的 offset store 里读回来的那个位点的部分——绝不会在 poll() 过程中提前释放，也不会仅凭"commit() 被调用了"就推进：Connect 在一次 flush 都没发生时同样会调用它。如果 task 在该 flush 完成之前崩溃并重启，同一个 CHANGES 窗口（或同一次快照）会在重启后被重放，产生重复记录。下游消费者应当基于记录的 key 做幂等处理，并按 Kafka partition 的顺序依次处理这些记录——重放会以相同的顺序重新投递相同的记录，因此按 key 的"后写覆盖前写"（last-write-wins）处理方式最终会收敛到一致结果——或者改为从经过压缩（compacted）的 topic 读取。不要通过要求 source.row_version 单调递增来做去重：它在不同记录类型之间不可比较（参见row_version 在不同记录类型中的表现），而且一次 UPDATE 的两条记录本来就会合法地共享同一个值。
  • 快照到增量的切换。 当 source.snapshot.mode=initial 时，第一次轮询为表创建 bookmark 并打开固定在该版本的 [_BOOKMARK_<id>_] 游标。每次轮询最多返回 source.snapshot.batch.size 条该表的 op: "r" 记录；游标跨轮询保持打开。所有快照行（包括最后一行）的 offset 都带 snapshot_done=false。读到 EOF 后，内存中的快照完成标志才翻转；下一次轮询以同一个 bookmark 为 base 读取增量，第一条变更记录的 offset 才带 snapshot_done=true。该标志由 Kafka Connect 的 offset flush 持久化。此前若崩溃或读取失败，快照从头重做，已交付的批次可能重复。
  • source.nontrackable.policy 控制当一个 CHANGES 窗口不再可读时应采取的动作（具体成因参见限制）：
    • fail（默认）：task 抛出异常并停止。需要人工介入——例如调大 source.bookmark.ttl.ms、修复根本原因，或者把该表切换为 resnapshot。
    • resnapshot：该表在内存中的位置会被丢弃，并在紧接着的下一次轮询中完全自动地基于一次全新快照重建。这并非没有代价：表越大，重新读取的代价也越大，表中目前仍存在的每一个 key 都会作为一条全新的 op: "r" 记录被重新投递，即便它之前已经被流式传输过一次——这在 at-least-once 语义下是可以接受的，但在大表或频繁触发 resnapshot 的表上，这一代价值得纳入考量。

6限制

  1. 只要还在轮询就会自动续租；轮询之间的长间隔仍会丢位点。 每一轮 poll 都会执行续租检查；一次续租轮（覆盖该 task 仍持有的每一个 bookmark，因为其中任何一个都可能成为重启恢复点）每授予租约的三分之一触发一次、并以五分钟封顶——但一轮只能发生在 poll 的开头，所以实际间隔是把 poll 间隔向上取整到该封顶值，因此只要 task 还在轮询，一张长期没有新版本的表也能保住自己的位置。续租节奏取的是服务端授予的租约的三分之一——而不是配置值，后者可能被集群侧的上限 bookmark_reference_max_ttl_ms 压低——续租失败不会被当作位置丢失处理：整轮全失败时指数退避重试——从一个 poll 间隔起步，租约未知阶段封顶一分钟，已知后封顶租约的三分之一。续租唯一覆盖不到的是没有在轮询的 task：Kafka Connect 的 pause 会停止调用 poll()，而本连接器的全部 JDBC 都跑在这条线程上，所以连接器被暂停（或停止、或删除）超过授予租约——source.bookmark.ttl.ms 与集群 bookmark_reference_max_ttl_ms 中较小者，任一侧取非正值即表示该侧不限——之后，bookmark 仍会失效，随后的 CHANGES 读取会判定为不可追踪并触发 fail/resnapshot。单次 poll 跑得比租约还长同样保不住——例如大表的初始快照——因为本连接器的全部 JDBC 共用 poll 线程，poll 进行中无法续租。存在长时间暂停、或快照耗时超过租约的部署，应调大 source.bookmark.ttl.ms，或把 source.nontrackable.policy 设为 resnapshot；注意 resnapshot 要求 source.snapshot.mode=initial（默认值），它与 no_snapshot 的组合会在启动时被 ConfigException 拒绝——没有快照可供重建，该表会静默跳过从已过期的 base bookmark 到新 bookmark 之间的全部变更。续租依赖集群提供 bookmark_renew；对不具备该函数的 StarRocks，每次续租都会失败并记录日志，空闲表的行为与此前一致。
  2. ts_ms 是处理时间，而不是提交时间。 它是连接器构建该记录时的墙钟时间（wall-clock time），并不是该变更在 StarRocks 中被提交的时间。
  3. DUPLICATE KEY / AGGREGATE KEY 表的 key 不唯一，且只支持插入工作负载。 它们的 Kafka key 是排序键或聚合键。DUPLICATE KEY 的排序键允许重复，多行共享同一个 Kafka key：分区和 key 内顺序仍然成立，但日志压缩会丢掉并非重复的行，开启 source.tombstones.on.delete=true 时一条墓碑会删掉与被删行同 key 的全部行。这类表也只有在纯插入（insert-only）工作负载下才是可追踪的：举例来说，对一张 DUPLICATE KEY 表执行 DELETE，会使对应的 CHANGES 窗口变为不可追踪（StarRocks 会报告 CDC-ERROR-1 (CHANGE_NOT_TRACKABLE): CDC for DUP_KEYS does not support delete）。AGGREGATE KEY 表报告的是（依据该表自身聚合函数计算出的）预聚合值，而不是原始插入的行。
  4. 空表的快照在重启后会被无害地重复执行。 依据上文所述的快照崩溃不变式，只要重启发生在 snapshot_done 被持久化为 true 之前，就会重做整个快照；对于一张目前还没有任何行的表，这只是一次没有实际效果的空查询，唯一代价是一次多余的往返请求。
  5. resnapshot 可能会重新投递已经发出过的变更。 失败窗口自身的记录会在策略生效之前先从本批次中丢弃，但更早那些窗口的记录已经进了 Kafka；随后的全量 resnapshot 会再次投递这些 key。这仍然在 at-least-once 的约定范围之内，但下游消费者应当对此有所准备。
  6. "不可追踪"的成因，以及该策略实际覆盖的范围。 除了空闲导致的 TTL 过期（第 1 条）之外，当自 base bookmark 以来底层数据的"形状"发生变化时，CHANGES 窗口也会变为不可追踪，例如：分区/表被 drop 或 truncate、schema 重写型的 ALTER TABLE（例如需要慢速 schema change 的类型变更）、bucket 数量变化或 reshard、不再能解析的 partition/tablet hint，或者窗口跨越了 enable_change_data_capture 被关闭又重新打开的一段时期。StarRocks 会以两种不同的形式报告这些情况——一种是 BE 执行期的 CDC-ERROR-<n> (CODE) 错误，另一种是 FE 规划期的拒绝，其错误信息中包含短语 "not trackable"——NonTrackableException.classify 能够识别这两种形式，以及过期/失效的 bookmark 引用，并把它们全部路由到已配置的 source.nontrackable.policy。任何其他 SQL 错误——即 classify 无法识别的错误——完全不受该策略覆盖，与 source.nontrackable.policy 的取值无关：这张表会在每次 poll 时重试，每次重试前先等一个 source.poll.interval.ms；持续失败达到 source.poll.retry.timeout.ms（默认 10 分钟）后 task 失败。正是这一步把永久性错误——列被 drop、权限被收回、bookmark 元函数被关闭——变成一个 FAILED 的 task，而不是一个一直 RUNNING 却永远不交付数据的 task。
  7. 完整的 CHANGES 窗口仍会整体物化在 worker 堆内存中。 快照已按每表每次 poll() 最多 source.snapshot.batch.size 条返回，但长时间中断后累积的 CHANGES 窗口仍可能耗尽堆内存。按变更量设置足够短的 source.poll.interval.ms。每张正在快照的表会占用一条读取连接直到 EOF；若批次之间暂停过久，其 bookmark 租约仍可能过期。
  8. 删除 connector 会让它当时仍然存活的 bookmark 一直被占用，直到其 TTL 过期。 并不存在一个注销（unregister）步骤，因此 connector 被移除时，其 task 当时仍然持有的那些 bookmark 会继续把对应的版本钉住、使其不被 vacuum 回收，最长可达授予租约（source.bookmark.ttl.ms 默认 7 天，并被集群 bookmark_reference_max_ttl_ms 压低）——两侧都不设上限时则会一直钉住。Task 重启则没有问题：启动时 task 会从 information_schema.table_bookmark_references 列出它的 holder 在这张表上仍持有的全部引用并悉数接管——据以恢复的那个 bookmark、窗口尚未落盘的 head、前一个 task 没来得及发出的释放——于是它们走正常的 commit 周期被释放，而不是等 TTL。删除 connector 则不然：之后没有任何东西再运行。
  9. 在 task 启动之后才给基表新增的列，要等到 task 重启才会被捕获。 每张表的 schema 只在 task 启动时解析一次，因此新增的列根本不会出现在发出的记录里。删除列的情况更糟：由于 connector 是显式投影列的，此后每一次轮询都会以 Unknown column 错误失败。对被捕获的表做过任何 DDL 之后，都应重启该 connector 的 task。
  10. Avro 要求 topic 名称本身是一个合法的 Avro schema 名称。 记录的 schema 名称是从 topic 名称派生出来的，因此带连字符（hyphen）的 topic——最容易通过 starrocks.table2topic.map 引入——会导致 AvroConverter 失败。只要 worker 使用的 converter 是 Avro，就应在 starrocks.table2topic.map 的取值以及 source.topic.prefix 中使用下划线而不是连字符。
  11. 在 Arrow Flight 通道上，驱动会把 DATETIME 按 worker 的 UTC 偏移量平移；连接器已将其逆转。 随包驱动（18.0.0）的时间戳访问器最后一步是 Timestamp.valueOf(LocalDateTime)，即无论传入什么 Calendar，都把存储的数字按 JVM 默认时区落值——UTC+8 的 worker 上早八小时（ArrowDriverResultSetTest 在进程内可复现）。连接器在 Arrow 通道上逆转这一步，两条传输打出同一串，冒烟的 parity 检查也把它比在内。唯一残留：处于夏令时区的 worker 在春季跳变那一小时内逆转不精确；给 worker 加 -Duser.timezone=UTC 连这一点也没有。DATE 与 MySQL 协议从来不受影响。
  12. no_snapshot 下，没有持久 offset 就必须读到引用列表。 若启动时无法读取 information_schema.table_bookmark_references，即使配置 latest 也会失败，因为无法判断 holder 是否还持有 bookmark。若列表为空，则按缺位点策略处理：fail 停止，latest 建立新起点，可能跳过旧引用过期以来的变更。

7Quick Start

本节完整走一遍在消息格式中用到的同一个 db1.orders 场景。

1. 一次性集群配置

ADMIN SET FRONTEND CONFIG ("enable_bookmark_meta_functions" = "true");
GRANT OPERATE ON SYSTEM TO USER 'root'@'%';

2. 创建一张开启 CDC 的 PRIMARY KEY 表，并写入一些数据

CREATE TABLE db1.orders (
    id INT NOT NULL,
    name VARCHAR(64),
    qty INT
) PRIMARY KEY (id)
DISTRIBUTED BY HASH(id)
PROPERTIES ("enable_change_data_capture" = "true");

INSERT INTO db1.orders VALUES (1, 'widget', 10), (2, 'gadget', 20);

3. 构建插件并启动 connect-standalone

mvn clean package -DskipTests
cp target/starrocks-connector-for-kafka-*-with-dependencies.jar /path/to/kafka-connect/plugins/

使用上文完整配置示例中的 source.properties 文件（把 starrocks.jdbc.url/凭据改成你自己集群的值），然后执行：

connect-standalone.sh worker.properties source.properties

4. 观察快照数据到达

kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic sr.db1.orders --from-beginning

会出现两条 op: "r" 记录，对应表中已有的两行数据，一行一条。

5. 产生变更并观察它们流式到达

INSERT INTO db1.orders VALUES (3, 'thingamajig', 30);
UPDATE db1.orders SET qty = 300 WHERE id = 3;
DELETE FROM db1.orders WHERE id = 2;

在 source.poll.interval.ms（默认 5 秒）之内，同一个 consumer 会依次打印：一条 op: "c"（对应插入）、紧接着一条 op: "d" 后跟一条针对 id: 3 的 op: "c"（对应更新），以及一条 op: "d"（对应删除）——从 StarRocks 表变更到 Kafka 消息的闭环就此完成。
