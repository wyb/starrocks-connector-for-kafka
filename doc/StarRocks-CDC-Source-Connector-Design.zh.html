本文描述连接器当前已实现的设计，而非最初的计划。使用方法见同目录下的《使用指南》；本文回答的是"为什么这样设计"。

1定位与范围

这是一个 Kafka Connect source 连接器，方向与本仓库已有的 StarRocks sink 相反：把 StarRocks 存算分离表的变更数据持续流出到 Kafka，一张表对应一个 topic。

它不新增 StarRocks 服务端能力，完全构建在已发布的原语之上：

原语作用
bookmark_create / bookmark_release元函数，在服务端钉住/释放一个版本位置，同时充当 vacuum 栅栏
[_BOOKMARK_<id>_]查询提示，读取该 bookmark 钉住的时间点快照
[_CHANGES_<base>_<head>_]查询提示，读取两个 bookmark 之间的增量变更
__CHANGE_TYPE__ / __ROW_VERSION__CHANGES 结果集的元数据伪列（0=INSERT/UPSERT，1=DELETE）

因此对服务端的唯一要求是：存算分离集群、开启 enable_bookmark_meta_functions、连接用户具备 OPERATE 权限、PRIMARY KEY 表提前打开 enable_change_data_capture。

设计取舍

曾评估过三条路线：① 在 StarRocks 内部实现订阅并直写 Kafka；② 引入 Flink 消费 CDC 再走 Flink-Kafka 生态；③ 写一个 Kafka Connect source connector 走 JDBC。

选择 ③ 的理由：不动服务端代码（① 需要在 FE/BE 里维护一套投递、重试、位点管理），不引入一整个计算引擎作为纯搬运层（②），并且可以直接复用 Connect 生态既有的 offset 存储、rebalance、SMT、converter、DLQ 与 exactly-once 框架。代价是数据要经过一次 JDBC 序列化——这也是后来引入 Arrow Flight SQL 通道的动机。

2总体架构

整体可以拆成两个方向相反的平面：数据面把行从 StarRocks 搬到 Kafka；控制面反向决定服务端的 bookmark 什么时候可以安全删除。前者直白，后者是设计里真正复杂的部分。

StarRocksCdcSourceConnector

为什么要拆

拆分之前 StarRocksJdbcClient 是 728 行、32 个方法，同时承担驱动注册、URL 解析、连接生命周期、leader 轮转重试、列元数据、类型映射、行提取和全部业务查询。最直接的证据是它的测试：为了测 URL 解析，测试得用反射撬开 private static 方法——需要反射才能测一个纯函数，说明边界画错了。现在 FeConnection.parseUrls 和 ColumnMetadataReader.toJdbcType 都是包内可见，直接调用即可。

为什么 Connector 要做 preflight

enable_bookmark_meta_functions 在 StarRocks 里默认是 false，这是首次部署最可能踩的坑。没有这个探测的话，配置校验通过、task 正常启动，真正的原因要到某次 poll 失败后、剥掉两层 getCause() 才能看到。preflight 用一次 bookmark 创建+释放（TTL 60s）把这件事提前到 start()。释放是 best-effort——能证明开关已打开的是创建，泄漏的探测 bookmark 60s 内自行过期。

不要"简化"掉的细节

preflight 的 holder 必须与 task 的 holder 不同（代码里是 PROBE_HOLDER_SUFFIX = ":preflight"）。bookmark_create 对同一 holder 是幂等的：当表的分区元数据未变、且该 holder 已经引用了最新 bookmark 时，FE 会返回已存在的那个 id。若 preflight 复用了 task 的 holder kc:<name>，那么任何一次 start()（重启、改配置、rebalance）都可能拿回 task 正在持有的 bookmark B，而 preflight 的释放会把 B 删掉——随后 task 恢复出持久 offset B，发起 [_CHANGES_B_head_]，得到 "bookmark B not found"。

这是实现过程中真实发生过的回归，由一次修复引入、又在集群冒烟里暴露出来。

3位点持久化：两个存储，一个 id

这是整个设计里最需要说清楚的一块：一次重启要正确恢复，依赖两处状态同时有效——Kafka Connect 侧记住"读到哪儿了"，StarRocks 侧还必须真的保留着那个位置。

连接器自己不做任何位点持久化——它只是把 bookmark id 塞进每条记录的 sourceOffset，剩下的交给 Connect 标准机制。真正需要连接器自己管的是右边那半：让服务端的 bookmark 在需要它之前不被删掉，在不再需要之后尽快删掉。

下面这张图是全文的骨架：一个 bookmark 从被创建到被释放，要穿过四个不同的线程。图里的颜色就是线程归属，后面 3.5 节会回到这一点。

3.1 写入路径

每条 SourceRecord 都背着自己的位置（ChangeRecordMapper）：

// 变更记录
sourcePartition = {"db": db, "table": table}
sourceOffset    = {"bookmark_id": head, "snapshot_done": true}

// 快照记录
sourceOffset    = {"bookmark_id": b0, "snapshot_done": false}

两个决定：

  • sourcePartition 按表拆分，而不是整个连接器一个位点。表之间因此互相独立，rebalance 把表重新分配到别的 task 上也能各自恢复。
  • bookmark_id 存的是窗口的 head，即"读到哪儿了"。重启后它成为下一个窗口的 base。

3.2 恢复路径

  1. start()拿到本 task 分到的表清单，逐表 reader.offset(sourcePartition(db, t)) 读回 raw map。
  2. restoreOffset()OffsetState.fromMap 解码，容忍 bookmark_id 被反序列化成 Integer 或 Long。
  3. restoreOffset()只信 snapshot_done=true：是则 committedBookmark = bookmark_id、snapshotDone = true；否则（含完全没有 offset）保持 fresh，下次 poll 重做整表快照。
  4. restoreOffset()把恢复出来的 bookmark 重新压回 liveBookmarks。
  5. poll()head = bookmarkCreate(...)；若 head == committedBookmark 则本轮无新版本，直接跳过（idle dedup）；否则读 [_CHANGES_base_head_]。
不变式 · 快照崩溃语义

快照行的 offset 一律 snapshot_done=false，变更记录一律 true。因此在"第一条变更记录的 offset 落盘"之前的任意时刻崩溃，恢复出来的都是 false，会整表重做快照，而不是接着一份投递了一半的快照往下走。宁可重复，不留静默空洞。

不变式 · 恢复的 bookmark 必须重新入队

第 4 步不是可选的。漏掉它的话，每次重启/rebalance/改配置都会在服务端留下一个孤儿 bookmark，钉住 vacuum 直到 TTL（默认 7 天）过期。这个 bug 真实发生过，是在集群冒烟日志里看到 21275 一直不被释放、而相邻 id 都正常释放才定位到的。

重新入队是安全的：commit() 只释放严格早于"上一轮 ack 水位"的 bookmark，所以这一个会一直活到更新窗口的记录被确认为止——那正是保护崩溃重放基点所需要的栅栏。

3.3 释放围栏：为什么要落后一个 commit 周期

Connect 的 commit() 只告诉你"某次 offset flush 完成了"，不告诉你是哪个 offset。同时，一个 bookmark 可能从未产生任何记录（空的 CHANGES 窗口也会推进 committedBookmark）。所以"保留最新 N 个"这类规则迟早会释放掉持久 offset 正指着的那个 base，重启就 CHANGE_NOT_TRACKABLE。

实现改为围绕真实的确认水位设栅栏：

状态含义
lastAckedBookmarkConnect 已确认过记录的最新 bookmark id，由 commitRecord() 维护。ack 水位，不是持久化水位——它跑在 producer 发送回调里，可能领先已落盘的 offset。
releaseFenceBookmark上一次 commit() 时观察到的 lastAckedBookmark。

每次 commit() 只释放严格早于 releaseFenceBookmark 的 bookmark，然后才把栅栏推进到当前的 ack 水位。中间隔开的这一个 flush 周期，就是"栅栏不会超前于持久化"的证明：任何在上一次 commit() 之前被 ack 的记录，其 offset 最迟在本次 commit() 之前的那次 flush 里已经落盘。

推论：什么都还没 ack 时不释放；commit() 第一次运行时也不释放。

commitRecord() 取 max 而非"最后一条"，因为同一张表的记录可能乱序 ack。

3.4 租约续期

bookmark_create 在表未变化时返回既有 id 但不刷新其租约，所以没有续期时， 空闲超过 source.bookmark.ttlms 的表会丢失位点。每轮 poll 在 drainPendingReleases 之后调 renewLiveBookmarks(t)：对该表持有的最老与最新两个 bookmark 调 bookmark_renew。最老的定住 vacuum 地板（fence 升序取第一个命中，更新的版本靠传递性 保留）且是重启恢复点；最新的是下一次 CHANGES 读的 base。中间那些不续：ack 水位可能永远够不到它们，全续等于 把它们钉住到 task 结束，而续租出现之前正是 TTL 在回收它们。

  • 节奏取服务端授予的租约的 1/3，不是配置值：真正决定过期的是 两者中较小的一个（任一侧 <= 0 按不限处理），而该上限是 mutable=true 的 FE 配置，随时可变， bookmark_renew 因此把生效值作为返回值带回。
  • 只有成功的轮次推进节奏时钟；全失败的轮次从一个 poll 间隔起步指数退避（租约未知时封顶一分钟，已知后封顶租约/3）， 瞬时故障秒级重试，没有 bookmark_renew 的旧集群渐近回到无续期时的节奏。
  • 续租失败不触发 source.nontrackable.policy：位点是否真丢了由下一次 CHANGES 读判定， 恢复入口保持唯一。
  • 续租只在 poll 线程发 SQL；锁内仅取 liveBookmarks 的首尾两个 id。单次 poll 长于租约 （如大表初始快照）时无法续租——见使用指南限制第 1 条。

3.5 线程模型

Connect 运行时会从三个线程调进来，而 JDBC client 是单线程的：

线程入口约束
task poll 线程poll()、bootstrap()、drainPendingReleases()、renewLiveBookmarks()所有 JDBC 都在这里
producer 回调线程commitRecord()只更新 ack 水位
SourceTaskOffsetCommittercommit()只入队待释放 id，不发 SQL

因此 commit() 授权释放之后，真正的 bookmark_release round trip 被推迟到下一次 poll() 开头的 drainPendingReleases() 执行。

  • liveBookmarks（ArrayDeque）、lastAckedBookmark、releaseFenceBookmark 三者共用 synchronized (liveBookmarks) 监视器。这是真并发，不是交错——早期版本没加锁，是设计缺陷。
  • pendingReleases 是 ConcurrentLinkedQueue，自身线程安全，不需要外部监视器。
  • 释放失败是 best-effort：记 WARN（带表名和 id），该 bookmark 挂到 TTL 过期。成功释放记 INFO——否则"没有释放失败"和"根本没尝试释放"在日志里无法区分，一个卡死的栅栏会看起来很健康，直到 vacuum 停止回收存储。

4顺序不变式

CHANGES 扫描的自然输出顺序是版本降序，且同一版本内 INSERT 在 DELETE 之前。直接透传是错的。所有 CHANGES 查询因此强制带上：

ORDER BY __ROW_VERSION__, __CHANGE_TYPE__ DESC

转成版本升序、同版本内 DELETE 先于 INSERT。这是正确性不变式，不是格式化偏好：一次 UPDATE 在下游必须表现为 op=d(旧值) 后跟 op=c(新值)。集群冒烟的 step 5 专门断言这一点，该子句一旦回归就会失败。

5记录格式

value 是标准 Debezium envelope，由 Debezium 官方的 io.debezium.data.Envelope 构建，而不是手工拼装。

为什么必须用官方 Envelope

该库拥有 envelope 的字段集合与字段顺序（before, after, source, op, ts_ms, transaction），以及各工厂方法打的 op 码。这个顺序是 Avro schema 身份的一部分，下游消费者和 schema registry 会拿它做比较；手写的 envelope 会静默漂移。此外 .Envelope 这个 schema 名后缀正是各类 SMT 判断"这是不是 Debezium 记录"的依据。

初版是手写的，后来改成标准实现。不要改回 SchemaBuilder/Struct 手工拼装。

字段内容
opr 快照 / c INSERT·UPSERT / d DELETE
before / after行 struct（optional schema，因为 c/d 各有一侧为 null）
source{db, table, row_version, bookmark: {base, head}}
transaction恒为 null——StarRocks 的 CHANGES 流不携带事务元数据
key主键列组成的 struct；无主键时为 null
复杂类型：先按文本承载，但把服务端的类型名留住

java.sql.Types 表达不了「这是 StarRocks 的 ARRAY」或「这是 HLL 草图」——它们全都是 OTHER，而在 MySQL 协议上，ResultSetMetaData 更是把它们和 VARCHAR 完全混同。所以 ColumnMeta 同时保留两套视角：JDBC 的，和 information_schema 给出的 DATA_TYPE（array/json/hll）与 COLUMN_TYPE（完整嵌套类型，如 array<int>）。

这也是两条通道都要查 information_schema 的原因：MySQL 通道仍用 ResultSetMetaData 定 jdbcType/精度/可空性，但额外查一次拿类型名。否则同一张表会因为 URL scheme 不同而产出不同的 schema——传输方式本该是实现细节，会改变 schema 的就不是。

ARRAY/MAP/STRUCT 目前发的是文本，但带上了 com.starrocks.data.* 逻辑名；JSON 用 Debezium 自己的 io.debezium.data.Json（JSON 列按定义就是 JSON 文档，这个承诺是安全的）。前三者不借用那个名字，是因为那等于承诺每个值都能按 JSON 解析，而 NULL、内嵌引号、深层嵌套这些边界尚未验证。srColumnType 已经留在 ColumnMeta 上，是为重建嵌套 schema 那一步准备的——注意 StarRocks 超过 15 层嵌套会渲染成 array<...>，将来的解析器必须对此显式失败而不是猜。

HLL / BITMAP / PERCENTILE 直接拒绝

这三种是聚合中间态，不是值：不配合聚合函数直接 SELECT，得到的东西消费者既解释不了也回灌不了。此前 preflight 只查表模型、CDC 属性和元数据列名冲突，所以带 HLL 列的表能顺利建起 connector，然后持续向 Kafka 发送无意义内容——从外部看和正常工作没有区别。现在在 preflight 拒绝并指明列名。

DATA_TYPE 为 unknown（StarRocks 新增了类型）不阻塞，但会记一条带 COLUMN_TYPE 的 WARN——值仍按文本保留，不至于丢，但值得在启动时说一次。

快照行的 row_version 必须是 0，不能是 bookmark id

变更记录的 row_version 是分区的可见版本号，从 1 开始逐次发布递增；而 bookmark id 来自 FE 全局 id 生成器，通常大几个数量级。把 bookmark id 放进这个字段，会让每一行快照数据看起来都比其后的所有变更更新——下游若按"仅当 row_version 增大才应用"去重，就会把全部变更丢掉。

快照行本就没有单一版本可报（钉住的读跨多个分区，各自处在自己的版本上），所以报 0。识别"这行来自哪次快照"应该看 source.bookmark.base/head，那两个字段才在 bookmark id 空间里。

source.tombstones.on.delete=true 时，每条 op=d 之后追加一条 value 为 null 的墓碑记录，与删除记录共享 key/topic/partition/offset，供 topic compaction 使用。

分区策略

不自定义 partitioner。key 是主键 struct，默认 partitioner 按 key 哈希——同一主键的所有变更因此天然落在同一分区，顺序得以保持。这正是下游需要的语义，自定义分区算法只会破坏它。

6双传输通道

数据面走哪条通道，完全由 starrocks.jdbc.url 的 scheme 决定，没有单独的开关配置：

两个驱动都打进了主 shaded jar。这是刻意的：一个"换传输方式还要手动补一个 jar"的连接器是部署陷阱；而未被 URL 选中的驱动是完全惰性的。代价是 jar 体积（Arrow 驱动本身约 42MB）。

两个踩过的坑

setFetchSize(Integer.MIN_VALUE) 是 MySQL Connector/J 的习惯用法，MariaDB 驱动会直接抛异常。（其 setFetchSize 字节码是 ifge → athrow "invalid fetch size"。）这个缺陷让流式读 100% 不可用，而且任何单测都抓不到——单测全部注入 FakeCdcClient。现在用正数 1024。

Arrow 通道的列元数据不可用，必须绕开驱动、改用 information_schema.columns 当普通行读。实测证据：一张 4 列的表，驱动报告 8 列，且全部 nullable=false、precision=0, scale=0。三个成因叠加——FE 的 ArrowUtils.convertToArrowType 给 FieldType 传了 metadata=null；驱动的 ConvertUtils 从不调用 Field.isNullable()（18.0.0 与 19.0.0 均如此）；prepared statement 路径把 schema 返回了两次。

不变式 · 列类型只有一个真相源

上面那条坑还有个后半段：schema 端换用了 information_schema，取值端却仍在问驱动。extractValue 曾经 switch 在 ResultSetMetaData.getColumnType() 上，而 ChangeRecordMapper 用的是 ColumnMetadataReader 给出的清单——同一条读取路径上两个真相源，其中一个已知在 Arrow 通道上不可信。两者一旦分歧，就是 schema 说 Date、值却是 String，在序列化时抛 DataException，且离成因很远。

现在 streamSnapshot/streamChanges 接的是 List<ColumnMeta> 而非列名，RowExtractor 按同一份清单取值，两边不可能再漂移。

BINARY / VARBINARY 走 BYTES

这两种类型曾经在 schema 端和取值端同时落到 STRING 默认分支，所以什么都不报错——字节被按连接字符集解码，非法序列变成 U+FFFD，原始字节不可恢复。两侧现已改为 Schema.BYTES + getBytes()；因为是两侧同时改，单独改一侧会立刻抛 DataException，这也正是新增测试所钉住的。

时间类型的读取统一传入一个每次新建的 Calendar.getInstance(TimeZone.getTimeZone("UTC"))，避免 worker 本地时区泄漏进结果。

FE leader 轮转

bookmark_create/bookmark_release 只能在 FE leader 上执行。客户端捕获 "must run on the FE leader"，关闭当前连接、轮转到下一个配置的 host 重试；轮转次数上限为 URL 个数，转满一圈仍未找到 leader 则抛出最后一个异常。其他 SQLException 则在同一 URL 上按 source.maxretries 重试。所以用户只需在 starrocks.jdbc.url 里列出全部 FE，不必自己指向 leader。

8交付语义与已知缺口

整体是 at-least-once。崩溃时未落盘的 offset 会导致从上一个已持久化的 bookmark 重新读一个窗口，重复投递已发出的记录。这也是"key 用主键 struct"重要的原因：PRIMARY KEY 表 + 主键 key 让下游可以幂等地应用。

Connect 的 KIP-618 exactly-once source 支持可以叠加，但需要 distributed 模式与相应的 worker 配置，本连接器没有做额外适配。

缺口 1 · 空闲表每次重启都会全量重做快照

唯一写 snapshot_done=true 的地方是变更记录。若快照做完后表一直没有变更，poll() 会命中 idle dedup（head == committedBookmark 直接跳过），一条变更记录都不发，持久 offset 就永远停在 snapshot_done=false。重启即整表重读。

语义上仍是 at-least-once（只是重复），但大表上代价不小。倾向的修法：让 bootstrap 结束时也能落一个 snapshot_done=true 的位点。

缺口 2 · bootstrap 未产生记录时，首个窗口持久化之前存在丢数据窗口

当 bootstrap 没有发出任何记录时——no_snapshot 模式，或者 initial 模式下快照时表为空——不会有任何 offset 落盘。若在第一个变更窗口被确认之前崩溃，重启会在当前版本重新开 bookmark，崩溃到重启之间的变更被静默跳过。

这一小段是 at-most-once，与整体语义不一致。窗口很窄（仅限首个持久 offset 出现之前），但确实存在。

以上两条均由代码推导得出，尚未编写复现测试；不是本轮改动引入的，是设计本身的推论。

不可追踪的处理

当 CHANGES 窗口跨越了破坏可追踪性的操作（PK 表 CDC 属性关闭期间的写入、DELETE/TRUNCATE 于非 PK 表、分区 drop/重写、schema 重写型 ALTER、bucket 数变更等），服务端报 CDC-ERROR-1 (CHANGE_NOT_TRACKABLE) 或 FE 规划期的 "not trackable"。NonTrackableException.classify 需要同时匹配这几类措辞——早期只匹配 CDC-ERROR- 前缀，导致 resnapshot 策略事实上从未生效。

9验证情况

单测覆盖状态机（注入共享的 FakeCdcClient）与纯函数部分，source + common 两个包共 80 个，整个模块 98 个。但状态机单测无法覆盖真实 JDBC 行为——setFetchSize 那个缺陷就是明证：它让流式读 100% 不可用，而全部单测照常通过。因此集成冒烟是必需的，不是补充。
